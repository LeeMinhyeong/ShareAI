# OAuth refresh safety and deployment limits

Before sending a refresh token, the router commits an SQLite intent keyed by a SHA-256 fingerprint of the provider and token. Intents are permanent, including after success. A second process encountering an existing intent fails closed; it does not wait for the first process or retry that token. Network errors, invalid responses, crashes after committing the intent, or failure to save a response require new OAuth credentials. Even a crash before the network request can require reauthentication. A provider which legitimately returns the same refresh token on success will consequently require reauthentication before it can be used again. These are deliberate availability tradeoffs, not proof of the provider's outcome.

Successful rotations are saved only if the credential ciphertext still matches the value reserved at the beginning of the attempt; a concurrent credential replacement is not overwritten. A successful rotation is saved even if the account was disabled during the request, but is not returned for use while disabled. This does not revoke an access token already returned before an administrator disables an account.

All refresh-capable processes for a given provider token must use this implementation and the same local SQLite database, with reliable locking and durable storage. Stop **all old processes** before upgrading: old code bypasses the intent entirely. Do not restore an older database snapshot, copy credentials into a separate database, delete intent rows, or allow other clients to use the same refresh token and expect this protection to hold. The intent table grows permanently; cleanup requires an independently justified token-retirement policy. Fingerprints are not encrypted; protect database access and backups. SQLite `synchronous=FULL` requests durable commits, subject to the filesystem and hardware honoring sync and locking. This does not establish exactly-once execution by the remote provider.

When a successful response omits `refresh_token`, OAuth permits a provider to retain the previous token, but the router cannot safely infer whether this provider consumed it. The router saves the new access token with no refresh token instead of replaying the old token. The account will require reauthentication when that access token expires; responses with a present but invalid refresh token are rejected and treated as uncertain. An unchanged returned refresh token is also not replayable because its intent remains permanent.

OpenAI access-token JWT payloads are decoded without signature verification and are not proof of authenticity. A finite numeric `exp` at or before the current time is used conservatively to reject the access token and, on an ordinary request, permit a serialized refresh even if `expiresAt` is in the future. A future JWT `exp` alone does not trigger the five-minute proactive refresh, avoiding extra rotation. Opaque, malformed, missing or nonnumeric JWT expiry falls back to stored `expiresAt` and the usual 401 handling; it does not establish that the token is valid. A stale 401 cannot rotate a newer internally refreshed credential. A refresh response containing an expired access token is first persisted with its rotated refresh credential, then rejected; a subsequent ordinary request can recover using that saved credential, subject to the intent and CAS protections above. Repeated provider responses with expired access tokens can still cause further rotations on later ordinary requests.

Account state has a monotonically increasing revision maintained by a SQLite trigger. Migration adds the column with default zero and preserves existing rows; legacy account-table migrations predate this change and have not been proven safe under simultaneous startup. Perform migration with a single stopped service before starting multiple processes. Test migrations against a backup, and ensure backups include SQLite WAL state. No production database was used for testing.
