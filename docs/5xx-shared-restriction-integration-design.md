# Shared 5xx restriction integration — historical design

**Current status:** The worktree now records confirmed inference HTTP 5xx in the existing v2 restriction store during OPEN settlement for ordinary and SIWC accounts. See [ADR 0012](./adr/0012-shared-5xx-restriction.md) and the README for the implementation, evidence and outstanding deployment blockers. The proposal below predates that integration; descriptions of which 429 table the current readers use are historical. It is not approval for deployment.

This is a proposed integration, not an implementation or a production safety guarantee. ADR 0008 decides the **429** policy; it does not authorize a 5xx retry or establish that a 5xx is account-local. The existing local backoff for confirmed 5xx starts at approximately 5–6 seconds, grows exponentially with jitter, and caps at 5 minutes; network errors are handled separately. That existing behavior is a possible starting point for a shared 5xx duration policy, not approval of a new policy or proof of account-local causation. The proposal below treats a confirmed provider inference HTTP 500–599 as a per-stable-account restriction on **new** requests. Scope, duration and recovery need explicit product approval; a provider-wide/global rule would require a different key and gate. User-approved automatic recovery and the priority of avoiding indefinite degradation must be preserved. Never resend the dispatched logical request on account of 5xx. The existing 401 reinvocation is a separate unresolved exception, not precedent for a 5xx resend.

## Why no partial activation

`forward-chat.ts` currently settles ordinary non-OK responses in `invokeOrdinary` and SIWC non-OK responses in the `infer` callback: only 429 arms `account_429_cooldowns`, and 5xx deletes OPEN without a durable restriction. Later local failure recording is not a cross-process fence. Both selection and writer-fenced admission read the old wall-clock-based 429 table, not `experimental_atomic_429_restrictions`. Writing a new restriction without changing **all** readers permits dispatch; changing only a reader without provisioning and migration can reject startup or lose old restriction evidence. `experimental-atomic-429-app.ts` already contains the relevant atomic ownership/generation/upsert/delete experiment for both account kinds, and `experimental-app-stopwatch.ts` and the coordinator explore monotonic expiry; duplicating those as another isolated implementation adds no integration safety. None is approved for production. The synthetic conversion is not a production migration.

## Concrete coordinated change

1. **Classification:** At the two physical inference `Response` sites in `forward-chat.ts`, classify `response.status >= 500 && response.status <= 599` before consuming the response and before clearing the attempt handle. Do not classify the locally synthesized 502/503 from fetch rejection, timeout, cancellation, invalid response, parser failure, refresh failure, or failed settlement as an upstream inference HTTP 5xx. Even a physical HTTP 5xx from a credential refresh is not an inference response and needs a separately approved scope and policy. A stream-level error inside an HTTP 200 is not a confirmed HTTP 5xx; keep its existing fail-closed attempt handling unless a separately specified evidence classifier is approved. Handle 429 independently, including the existing SIWC stream-429 path. A 5xx must not enter either selection-loop reselection path or the separate 401 refresh/reinvocation branch.
2. **One durable representation:** Design a production-named restriction table keyed by `(kind, account_id)` with `kind` restricted to `upstream`/`siwc`, a positive signed-64-bit generation, and a nullable signed-64-bit monotonic duration (NULL means indefinite). Maintain one persistent singleton version and nonnegative signed-64-bit generation counter; allocate a fresh generation on **every** arm, including extension, reject exhaustion and invalid state rather than wrapping or converting through JavaScript Number. Keying by stable ID preserves restrictions over credential rotation and ID deletion/reinsertion. Overlap takes the maximum full duration; indefinite dominates. If 429 and 5xx share a row, this rule must preserve both and restart observation on every generation; alternatively use separate reason-keyed rows and require all active reasons to clear. Do not let a 5xx arm shorten a 429.
3. **Atomic settlement:** Promote/adapt (do not directly activate) the algorithm in `src/db/experimental-atomic-429-app.ts`: within `withAsyncWriter`'s acquired `BEGIN IMMEDIATE`, validate schema/state and the exact `(account_id, attempt_id)` owner in `main.ordinary_account_attempts` or `main.siwc_account_attempts`; allocate the generation, upsert the conservative restriction, then delete exactly that owned OPEN and require one affected row for each conditional write. Any error must escape the callback and roll back all three mutations. Await the confirmed commit without the client abort signal before clearing the local attempt handle or publishing the result. An uncertain commit/close acknowledgement means unknown outcome for either account kind, including SIWC streaming: do not replay the dispatched request, claim persistence, or separately delete OPEN; preserve the local OPEN handle/evidence and return/close with an internal failure where still possible. The durable OPEN may already have been deleted by a commit whose acknowledgement was lost; do not claim it remains in that case. Retain OPEN on pre-commit failure. Do not expose raw provider data in rows or logs.
4. **Call sites:** Replace the inline ordinary `settleAccountAttempt` 429 callback and private SIWC `settleSiwc` restriction branch with the same typed settlement API for both confirmed 429 and confirmed 5xx. Keep plain successful/known non-restricted settlement distinct; do not invoke it after a restricted settlement fails. Preserve cancellation-independent cleanup and existing SIWC ACL, pinning, credential revision and ordinary credential/quota checks. Inspect every network initiation site, including the separate 401 path, for an equivalent final gate before shipping.
5. **Gates and visibility:** In `src/account-pool/manager.ts` make both kinds' candidate filtering test presence of the new restriction, not an absolute wall deadline. In `src/upstream/account-quota.ts` check it at both the reservation transaction and the writer fence immediately before `start()`. In `forward-chat.ts` check it in both SIWC admission and the second writer fence immediately before `start()`. Preserve the existing rule that reselection is allowed only after a confirmed committed read-only admission result, never after reservation or uncertain commit, and never for pinned SIWC. Update `src/routes/routing-snapshot.ts` to represent active new restrictions without inventing a wall-clock expiry. Advisory selection does not replace the writer gates. Stop all old writers for the offline cutover and prevent their restart or rollback to old binaries afterward; old code has no marker enforcement and can bypass new gates. This requires an external deployment fence, not an assumed database marker. Do not silently dual-read by elapsed wall time.
6. **Provisioning and migration:** Extend `src/db/client.ts` startup validation/provisioning with the new marker and exact schema/constraints/index validation, atomically provisioned only for genuinely empty databases. Reject missing/partial/unknown markers and incompatible schemas before persistent mutation, including journal mode, as a requirement—not a guarantee of the current implementation. A read-only preflight followed by reopening for `journal_mode` has a TOCTOU gap and does not satisfy it: a concrete, independently reviewed mechanism must bind validation to the exact database identity and exclude replacement or concurrent mutation through the first write (including journal-mode changes), or startup must fail without that write. No such mechanism is established here. For existing databases, require a separately reviewed offline upgrade with all old and new writers stopped and externally fenced, provenance and restorable consistent backup verified, and an atomic validated conversion of **every** legacy `account_429_cooldowns` row, including expired-looking or orphan rows, into conservatively retained restrictions; preserve both OPEN tables and all unrelated evidence. Legacy `until_at` does not establish a safe elapsed duration. If conversion retains rows indefinitely because their timing cannot be trusted, this is not an acceptable automatic-recovery policy: activation additionally requires an independently designed, controlled recovery for those legacy restrictions and explicit operator acceptance; do not silently leave accounts degraded forever. Validate raw IDs and all legacy rows/schema before conversion and fail closed on ambiguity. The experimental JSON planner/converter is not a migration and cannot establish provenance. Do not run mixed binaries, restore stale snapshots, or allow old binaries to bypass new gates; backup restoration must itself follow a reviewed recovery procedure.
7. **Expiry:** No `Date.now()` deadline may clear a new restriction. The generation-based monotonic observer/scheduler remains experimental, not production functionality. An indefinite 429 intermediate would conflict with the user-approved automatic recovery; do not enable this integration until a reviewed recovery mechanism and policy are available rather than replacing automatic recovery with indefinite degradation. The existing 5xx backoff is a candidate baseline, subject to approval and correct shared enforcement. A future observer must start the full duration after first observing each committed generation, restart the full wait on process restart or generation change, sample a validated monotonic clock inside the expiry writer transaction, and delete only with a matching generation. Clock faults fail closed; lock contention must not silently reset or shorten the wait. Clock suspend/VM rollback assumptions, fairness/capacity, lifecycle and shutdown need explicit review. Automatic recovery is routing policy, not proof of provider authorization or account-local scope.

## Acceptance evidence before activation

With user approval for new regressions and independently reviewed fixture isolation, use synthetic credentials, provider and databases only. Red-first tests must exercise authenticated production routing in separate router processes: each account kind receives exactly one real synthetic HTTP 5xx, restriction and owned OPEN transition atomically, a subsequent new request is rejected/reselected according to the approved scope, and restart preserves it. Include a successful dispatch positive control; pinned SIWC and revoked ACL; 429/5xx overlaps in both orders; credential rotation and stale success; network failure and synthetic local 502/503 not classified as confirmed 5xx; no resend; cancellation and already-sent SSE output. Pause after selection and commit the restriction from a separate writer before each actual admission/dispatch fence; assert zero calls for the blocked account.

Inject a statement failure after generation and restriction writes but before OPEN deletion, observe those provisional writes on the writer connection, and verify rollback of transactional rows/schema/index metadata after reopening; test journal-mode non-mutation separately, since it is not covered by that transaction. Separately simulate lost commit acknowledgement through the real caller for both account kinds, including SIWC streaming, and verify no follow-up dispatch or separate OPEN cleanup; distinguish that simulation from real disk faults. Exercise stale generations, overflow, indefinite and long/short overlap, clock faults, actual SQLite contention, restart and migration conflicts. Validate migration against real application-schema synthetic fixtures and compare durable state before/after rejection. Exercise the eventual preflight solution against replacement/concurrent-mutation races, and verify old writers cannot restart or roll back after cutover. Demonstrate approved automatic recovery, including separately controlled recovery of legacy restrictions, before activation. Independent review precedes final acceptance tests. Respect the currently pending approval for 5xx regression-test creation and do not run blocked commands or use real services, preserved fixtures, reserved ports or system temp.
