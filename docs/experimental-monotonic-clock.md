# Experimental monotonic cooldown clock — not production-ready

This is an offline foundation, not integrated into the application. Run `node --test tests/experimental-monotonic-clock.test.mjs`. Tests create a private scratch SQLite database, actual separate router workers and a separate named-pipe service; no production database, secrets, services, or port 20128 are used. Test IPC controls a virtual source hosted in the clock worker; the service protocol itself has no clock-control operation. The test simulates a 121-second wall jump by replacing `Date.now` in those processes, not by changing the OS clock. A second test runs the actual `process.hrtime.bigint()` source in a separate clock process.

A service process calls `serveClock`, obtains a random 256-bit epoch and produces nonnegative integer nanosecond readings. It must remain alive: restarting creates a new epoch. Routers obtain a new IPC reading before each database writer transaction. SQLite stores signed 64-bit INTEGER deadlines and reads them via `safeIntegers()`. A 429 observer calls `limit` **after** observation, with a positive bigint nanosecond duration rounded upward by the caller; the clock reading then comes after observation. It adds a nonnegative margin and updates the max deadline inside an immediate transaction. `allowed` treats a sample taken before acquiring the writer conservatively: staleness cannot make an expiry earlier. Age uses the local monotonic clock and is bounded in the writer. The connection's busy timeout is reset to zero; contention is a failure, not a synchronous wait or an RPC inside a transaction.

Missing, stale, malformed or disconnected clock reads and SQLite failures result in `allowed` returning false. `limit` throws on failure and returns false on an epoch mismatch; callers **must treat either as an unresolved restriction**, not dispatch. Existing different-epoch rows are retained, never replaced with an apparently shorter new epoch. Even already expired old rows remain blocked after service restart; recovery requires a separate safe policy not provided here. Same-service router restarts retain validity.

## Test-only vertical simulation

Run `node --test tests/experimental-monotonic-clock.test.mjs tests/experimental-monotonic-vertical.test.mjs`. The vertical fixture runs two separate synthetic HTTP routers, a local synthetic provider, SQLite, and a separate clock process. It commits a test-only per-account OPEN row before dispatch, holds after real 429 response headers, and proves the second process sends to B while A remains OPEN. A competing SQLite writer blocks finalization; the test verifies a busy attempt and advances virtual monotonic time before release, then checks the committed deadline. A separately captured sample is rejected as stale after a real elapsed wait and contention. It also tests real elapsed expiry, simulated forward/backward wall changes, a router restart and a new clock epoch. These are fixture semantics, not the production `/v1` route: selection and claim are not an atomic production authorization gate, and the fixture is not evidence of crash-safe or production-safe integration. In particular, service restart between clock sampling and the SQLite commit or dispatch remains an unresolved TOCTOU risk; neither freshness nor this test closes it.

## Trust and remaining safety gaps

- The test uses a random named pipe and synthetic shared token passed in child environments. The token checks the *client request* only; the response is not authenticated and the endpoint could be impersonated. There is no verified Windows pipe ACL, safe token distribution, peer identity, server authentication, anti-replay, or secrecy from local processes. Windows named pipes are not filesystem paths beneath scratch. OS isolation and producer authentication are unproven; do not use this as a trusted production clock.
- A fresh read proves only a response was received; service death, replacement, or compromise can occur immediately afterwards. The bounded local age is not an atomic liveness guarantee. Coordinating service ownership and dispatch across the reading/writer boundary requires further design.
- If recording a 429 fails before a durable row exists, this module cannot by itself tell other routers that a restriction is unresolved. A durable fail-closed intent/fence, crash recovery, and complete 429-to-dispatch integration are essential before production. Calling `allowed` independently after ignoring a failed `limit` is unsafe.
- No suspend/resume or host reboot semantics are established; monotonic-clock suspend behavior is platform-dependent. All router/service machines must be the same trusted OS instance and epoch must never be persisted or reused across service restarts. Restriction resolution across reboot is out of scope.
- Tests do not prove hostile-local-process resistance, clock liveness during a transaction, real OS clock changes, concurrency of overlapping 429 observations, or production integration. No service supervisor, deployment mechanism, recovery policy, or security review is included. Defaults (zero margin, one-second sample age) are experimental and not validated for production.
