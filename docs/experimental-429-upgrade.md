# Synthetic legacy 429 conversion experiment

**Not a production migration or a security sandbox.** This module is not wired to startup, routing, scripts or a CLI. The exported function accepts exactly one JSON string containing synthetic fixture rows; it creates, owns and closes a fresh `:memory:` SQLite connection on every call. No connection, SQL, callback, attachment, temporary object, trigger, schema or database path can be supplied through this interface. Unknown fields are rejected. It is an experiment over a reduced frozen model, not a recognized application schema.

Input is an object with `legacy` (arrays of kind, account ID and decimal signed 64-bit deadline strings), `ordinaryOpen` and `siwcOpen` (arrays of account ID and attempt ID strings), and optionally boolean `failAfterWrites`. It returns a conversion status and before/after snapshots with BigInt integer values; malformed fixture shapes or setup failures throw. `failAfterWrites` causes a deterministic simulated exception after marker and restriction writes, then exposes the rolled-back snapshot. This does not simulate a disk or commit failure. The snapshots cover fixture rows, schema, index metadata, temp schema, attached databases and relevant connection metadata.

Within a SQLite `BEGIN IMMEDIATE`, the experiment validates its internally created fixture and converts every legacy row, including expired-looking and orphan rows, to an indefinite restriction using the exact kind and ID; it preserves legacy and OPEN rows. Each invocation creates a new fixture, so re-upgrade, hostile schema and outer-transaction scenarios are not exposed or tested. Input cannot represent invalid UTF-8 storage, arbitrary SQLite storage classes, triggers or attached/temp databases; unknown field tests establish API rejection, not validation of such databases.

## Separate read-only JSON planner and compatibility fixture

`experimental-429-legacy-plan.mjs` is a **read-only planning exercise on supplied JSON only**. It cannot prove input completeness, source SQLite raw UTF-8 bytes, the source schema, or production safety. The compatibility fixture explicitly projects five columns: additional database columns would be hidden from the planner's unknown-field check. Conversion through JavaScript strings and JSON does not preserve or validate original SQLite storage bytes. The planner validates `observed_at`, `until_at`, and `revision`, but omits them from its output; its proposals are not a lossless representation or a migration.

The synthetic real-app fixture compares selected logical snapshots: main schema, main table rows, integrity and foreign-key checks, and journal mode, before and after planning. An unchanged selected snapshot is not proof of byte-identical files or all database state, and **no migration is performed**. If database close fails, or the previous working directory cannot be restored, cleanup retains the fixture directory and reports its location; primary and cleanup errors are preserved together. The injected close-failure test exercises that cleanup decision, not a real SQLite close failure.

This API is not a security boundary against malicious code in the same process, compromised dependencies, monkey-patched runtime, resource exhaustion, or physical storage faults. It provides no production migration protection, provenance, backup verification, writer fencing or recovery guarantees. A real deployment needs a separately designed and reviewed migration, a verified restorable consistent backup, and operational stop/disable and fencing procedures for all writers; a temporary writer lock or caller declaration is not evidence of those safeguards.
