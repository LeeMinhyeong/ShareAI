# ADR 0017: 공급자 스트림 정리는 best-effort다

**상태:** 기록(2026-11-10). 결정 자체는 2026-11-03 보안 요구로 도입된 기존 동작이며, 이 ADR은 그 결정을 사후 문서화한다.

## 맥락

공급자 응답 본문(`response.body`)과 SSE 리더(`reader`)는 오류·잘못된 content-type·소비자 `return()`·라우터 중단 시 취소해야 한다. 과거 구현(HEAD)은 `await reader.cancel()`로 취소 완료를 기다렸다. 그런데 `cancel()`은 신뢰할 수 없는 상대(공급자 연결, 중간 프록시, 테스트 픽스처)가 끝내 settle하지 않을 수 있다. 이를 기다리면 클라이언트 응답과 요청 종료가 무기한 붙잡힌다.

2026-11-03 보안 요구: "신뢰할 수 없는, 끝나지 않는 취소를 기다리느라 의도한 일반 오류의 반환을 무기한 미루지 않는다." 당시 확인 결과 `inference.ts`는 잘못된 content-type 경로와 스트림 파서 모두 취소를 시도만 하고 기다리지 않았다.

## 결정

1. 공급자 본문과 리더의 취소는 **시도만 하고 기다리지 않는다**(`void x.cancel().catch(() => {})`, 동기 throw도 삼킴). 관측된 결과(상태 코드, 파싱 오류, 터미널 이벤트)는 취소 완료를 기다리지 않고 즉시 호출자에게 전달된다.
2. 취소가 늦게 resolve 또는 reject되어도 정산 결과(OPEN, v2 제한, 사용량 기록)는 바뀌지 않는다. 늦은 rejection은 처리되며 unhandled rejection이 되지 않는다.
3. 안전성은 취소 완료가 아니라 **오류 분류**로 보장한다. 신뢰할 수 없는 실패 봉투나 잘린 스트림은 502(비브랜드)로 분류되고 불확실 OPEN을 유지한다(ADR 0008). 따라서 취소가 끝나지 않은 동안에도 같은 계정으로 다시 발송되지 않는다.
4. 취소가 실제로 소켓을 회수했다는 보장은 없다. 회수는 런타임(undici)의 연결 정리에 맡긴다.

## 대안

- **취소 완료 대기(이전 HEAD):** 자원 회수는 확실하지만, 끝나지 않는 취소 하나가 요청·종료를 무기한 붙잡는다. 거부.
- **제한 시간이 있는 대기:** 지연 상한은 생기지만, 상한 동안 응답이 늦어지고 시한 뒤의 동작은 결국 1번과 같다. 이득 대비 복잡도가 커서 채택하지 않음.

## 결과와 검증

- `tests/siwc-stream-cancel.test.mjs`: 신뢰된 SIWC 429, 신뢰할 수 없는 봉투, 소비자 `return()`이 모두 멈춘 취소를 기다리지 않고 결과를 낸다. 취소는 시도되고, 늦은 rejection이 unhandled가 되지 않는다.
- `tests/phase4-siwc-stream-durable.test.mjs`: 라우트 수준 사례. 멈춘 취소에서도 502가 즉시 반환되고, 불확실 OPEN이 유지되며 v2 제한은 없고, 취소가 끝나기 전 재발송이 없다. 늦게 취소가 reject되어도 OPEN, 제한, 사용량이 그대로다.
- 한계: 소켓 누수 여부(장시간·대량)는 검증하지 않았다.
