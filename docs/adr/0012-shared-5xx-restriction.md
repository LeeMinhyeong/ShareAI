# ADR 0012: 확인된 추론 HTTP 5xx의 공유 계정 제한

## 상태

작업본에 부분 구현 및 집중 테스트 완료. 운영 배포·기존 DB 전환은 승인하지 않는다. 전체 Phase 4 테스트와 실제 제공자 검증은 남아 있다.

## 배경

확인된 추론 HTTP 5xx 후 OPEN을 정리해도 쿨다운은 프로세스 로컬에만 있어 다른 프로세스나 재시작한 프로세스가 해당 계정을 즉시 다시 선택했다. 사용자가 별도 세션에서 작성한 합성 다중 프로세스 테스트로 이 문제가 재현됐다. 5xx만으로 요청이 실행되지 않았다고 판단할 수 없으므로 이미 발송한 논리 요청의 재발송은 허용하지 않는다.

## 결정 및 구현 범위

- 실제 추론 응답의 HTTP 500–599에만 제한을 설정한다. 로컬에서 만든 오류나 네트워크 실패를 제공자가 반환한 HTTP 5xx로 간주하지 않는다. HTTP 200 본문의 스트림 오류는 이 분류에 포함하지 않는다.
- 기존 `account_429_v2_restrictions` 저장소를 일반·SIWC 계정별 공유 제한에 함께 사용한다. 기존 이름은 유지되지만 이제 429와 5xx를 모두 나타내며 행만으로 원인을 구분할 수 없다. 관리 화면의 `restricted` 역시 원인을 구분하지 않는다. 별도의 스키마 변경은 추가하지 않았다.
- 소유한 OPEN 검증, 제한 arm 및 정확한 OPEN 삭제를 같은 `withAsyncWriter` 트랜잭션에 넣는다. 오류는 트랜잭션을 실패시키며 실제 커밋 결과가 불명확하면 제한이나 OPEN의 최종 상태를 확정하지 않는다. 기존 writer의 정리·격리 계약은 그대로 유지한다.
- 429와 5xx의 제한이 겹치면 기존 저장소의 규칙대로 긴 전체 기간을 유지하고, 어느 쪽이든 기한이 불명확하면 불명확한 상태가 우선한다. 저장된 제한의 관찰·만료는 기존 v2 단조시계 경로를 사용한다. 새 프로세스가 해당 generation을 처음 관찰하면 전체 기간을 다시 기다린다.
- 기존 로컬 백오프를 기준으로 첫 5xx에는 6초를 기록한다. 이는 기존 5–6초 범위의 상한이다. 같은 프로세스가 유지한 같은 revision의 연속 실패 수에 따라 기존 지수 백오프의 지터 상한을 사용하고 5분을 넘기지 않는다. **공유되는 것은 제한 기간이지 연속 실패 횟수가 아니다.** 실패 횟수는 프로세스별 메모리 값이므로 다른 프로세스와 재시작 후에는 지수 단계가 달라질 수 있다.
- 제한의 적용 범위는 라우터의 계정별 가용성 정책이며, 제공자 장애가 실제로 계정 단위라는 증거나 다른 계정을 통한 요청이 제공자 정책상 허용된다는 뜻이 아니다. 이 작업은 기존의 별도 401 갱신 경로를 승인하거나 변경하지 않는다.

## 대안과 영향

별도 5xx 전용 제한 테이블은 원인과 연속 실패 수를 구분할 수 있지만, 추가 스키마와 기존 DB 전환·모든 읽기/발송 게이트의 동시 변경이 필요하다. 이번 작업본은 이미 연결된 v2 저장소를 공유해 읽기·만료 경로가 다른 테이블을 바라보는 부분 전환을 피한다. 대신 원인별 상태 표시와 프로세스 간 지수 실패 횟수 보존은 제공하지 않는다. 사용량·제한 이력 전환과 구버전 프로세스 차단은 별도 운영 차단 사항이다.

## 검증 및 한계

사용자가 제공한 수정 전 일반 계정 테스트에서 다른 프로세스와 재시작 프로세스가 A를 다시 호출하는 실패가 재현됐다. 수정 후 부모가 직접 실행한 집중 테스트는 Node 집계 10/10 통과: 테스트 전용 파일 SQLite와 별도 라우터 프로세스를 사용해 A 단일 발송, B 선택, 재시작 후 B 선택, 네트워크 실패 OPEN 유지, 로컬 503 미발송, SQL 문 오류 롤백 및 기존 유한·무기한 429 제한과의 중첩을 확인했다. HTTP 요청·응답과 제공자는 모의했다.

SIWC의 HTTP 503 제한·6초 경계 및 SQLite 문 오류 롤백은 메모리 SQLite, 합성 제공자와 모의 응답을 이용한 인증 집중 테스트 5/5 통과에 포함된다. 실제 디스크·전원 장애, 제공자 정책 및 호환성, SIWC 다중 프로세스·재시작, 외부 클라이언트 재시도 중복 제거는 이 결과로 증명하지 않는다.
