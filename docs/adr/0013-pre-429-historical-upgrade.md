# ADR 0013: 429 도입 이전 DB의 오프라인 전환

## 상태

작업본에 구현 및 격리 집중 테스트 완료. **오프라인 429 CLI는 계속 비활성화**되어 있으며, 운영 적용과 실제 DB 전환은 별도 승인 전 금지한다. Phase 4 전체 완료를 뜻하지 않는다.

## 배경

`740df936887f40efc727a24b159064bfd4db34e5`의 초기화 스키마에는 `account_429_cooldowns`가 없다. 기존 OPEN 스키마 도구는 해당 과거 스키마에 OPEN과 마커를 추가하지만 cooldown 테이블을 만들지 않는다. 이후 기존 429 전환은 이 테이블을 필수로 요구해 거부한다. 테스트 소유 파일에서 실제 OPEN 도구를 거친 뒤 누락된 cooldown 검사에 도달해 거부되는 것을 재현했다.

## 결정

기존 다섯 가지 전제와 별도로 `--genuinely-pre-429` 확인을 받은 경우에만, 기존 DB가 지정된 `740df93` 초기화 스키마에 현재 OPEN 도구가 pre-OPEN 경로로 추가한 정확한 객체들을 더한 형태인지 검증한다. 정확한 SQLite 저장 SQL과 객체 목록을 비교하므로 동등한 다른 형식의 DB도 거부할 수 있다. `quota_migration_marker`와 두 OPEN 마커, UTF-8 및 DB 메타데이터, 무결성 및 외래 키를 확인한다. 부적합하면 거부한다.

검사와 빈 legacy cooldown 테이블 생성, 기존 v2 제한 및 사용량 전환, 최종 검증은 동일한 최상위 IMMEDIATE 트랜잭션에 둔다. 이후의 전환 로직을 별도로 우회하지 않는다. 실패 시 롤백을 시도하며 커밋 오류나 정리 실패는 결과가 불확실할 수 있다. 기존에 cooldown 테이블이 있는 전환 경로는 이 옵션 없이 그대로 사용한다.

**스키마만으로 과거 출처를 증명할 수 없다.** 나중에 cooldown이나 다른 안전 이력이 삭제된 DB도 같은 모습일 수 있다. 운영자는 진정한 pre-429 DB임을 독립 확인하고, 검증 가능한 백업·모든 구버전 라우터 및 미해결 작업 중단·보호된 디렉터리 등 기존 조건도 충족해야 한다. 운영자 확인은 프로그램이 검증한 사실이 아니다. 출처를 확인할 수 없다면 전환하지 않는다. 이 결정은 자동 복구나 구버전 재접속 차단을 주장하지 않는다.

## 대안과 영향

누락 테이블을 조건 없이 빈 테이블로 만들면 손실된 제한 이력을 정상으로 오인할 수 있어 거부한다. 반대로 모든 pre-429 DB를 계속 거부하면 알려진 실제 구버전에서 전환할 수 없다. 엄격한 스키마 일치와 별도 출처 확인을 요구하는 제한적 경로를 선택했으며, 다른 합법적 과거 스키마의 호환성은 보장하지 않는다.

## 검증과 한계

Windows 테스트 소유 파일에서 저장된 `740df93` 전체 초기화 스키마와 합성 데이터를 사용해 기존 OPEN 도구 실행 → 429 helper 전환 → 별도 프로세스에서 실제 현재 DB initializer 실행을 확인했다. 집중 테스트 1/1 통과. 원본 행과 2^53을 초과하는 64비트 사용량, 출처 불명 `usage_known`, 외래 키를 확인했다. 별도 출처 확인 누락, 예상 밖의 뷰, 필수 마커 누락은 거부하며, cooldown 테이블 생성 직후 주입한 JavaScript 예외의 전체 스키마·행·저널 롤백을 확인했다. 원래 사용량 전환 회귀 10/10도 통과했다.

초기화는 Node의 TypeScript 변환과 테스트용 모듈 해석기를 사용했으며 실제 서버 리스너나 제공자는 실행하지 않았다. 네트워크·자식 프로세스 차단은 JS 가드이지 OS 샌드박스가 아니다. 실제 운영자의 과거 DB, 별도 프로세스 간 시작 경합, 경로 교체·reparse 경합, 실제 디스크·전원 장애와 구버전의 재접속 방지는 검증하지 않았다. 다른 과거 스키마나 손실된 기록의 복구도 범위 밖이다.
