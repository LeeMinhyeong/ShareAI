# ADR 0018: 새 DB 생성과 기존 DB·메모리 DB 범위

**상태:** 결정(2026-11-10, 사용자 승인). 운영 전 단계이므로 DB 구조는 요건에 따라 계속 바뀔 수 있다는 전제다.

## 맥락

Phase 4 작업본의 `client.ts`는 DB를 `fileMustExist`로 열고, 열자마자 429 v2·OPEN 안전 스키마 표식부터 검사한다. 커밋된 버전은 폴더와 파일이 없으면 자동으로 만들었다. 이 변경으로 다음 문제가 생겼다.

- 서버 시작이나 `npm run db:migrate`로는 새 DB를 만들 수 없어, 신규 설치가 불가능했다. README는 여전히 `db:migrate`로 초기화하라고 안내하고 있었다.
- 안전 스키마가 없는 기존 DB를 다루는 테스트 약 15개가 실패했다. 원인은 두 갈래였다. 하나는 거부는 되지만 v2 검사가 먼저 실패해 거부 사유가 바뀐 경우, 다른 하나는 꺼져 있는 업그레이드 경로를 실제로 실행하는 경우다.
- 메모리 DB(`sqlite::memory:`)는 항상 비어 있어서 안전 스키마를 가질 수 없으므로 원리상 항상 거부된다.

자동 생성을 막은 이유는 이렇다. 경로 오타나 마운트 누락이 있으면 빈 DB가 조용히 새로 생기고, 그러면 기존 OPEN 표식과 429 제한이 사라진 것처럼 보여 결과가 불확실한 계정에 요청을 다시 보내게 된다.

## 결정

1. **새 DB는 `npm run db:init`(`src/db/init.ts`)으로만 만든다.**
   - 경로에 아무것도 없을 때만 새 파일을 만든다(`O_EXCL`, 모드 0600, 필요하면 상위 폴더 포함). 빈 파일을 포함해 이미 있는 경로는 거부하고 건드리지 않는다. 옆에 남은 `-wal`·`-shm`·`-journal` 파일이 있어도 거부한다.
   - 동시에 두 번 실행하면 하나만 성공한다. 실행 중에는 서버를 시작하지 않는다(WAL 전환이 BUSY로 실패할 수 있음).
   - 안전 스키마(`provisionFreshSafetySchema`)를 IMMEDIATE 트랜잭션 하나로 넣은 뒤, 일반 초기화(`initDatabase`)로 나머지 스키마를 만들고 검증한다.
   - 안전 스키마가 커밋되기 전에 실패하면, 이 명령이 배타적으로 만든 파일만 지운다. 지우지 못하면 원래 오류와 함께 보고한다. 커밋 뒤에는 다른 프로세스가 이미 쓸 수 있으므로 지우지 않는다. 그 뒤 나머지 초기화가 실패하면 `db:migrate`로 마저 진행할 수 있다.
   - 서버 시작과 `db:migrate`는 지금처럼 기존 파일만 연다.
2. **기존 DB 업그레이드는 Phase 4 범위 밖이다.**
   - 거부 동작은 계속 테스트로 지킨다.
     - 특정 검증기를 확인하는 테스트는 fixture를 "안전 스키마가 있는 DB + 해당 손상"으로 바꿔, v2 검사 뒤의 검증기가 실제로 실행되게 했다(`account-429-migration`, `phase2-quota-migration-safety`, `phase4-ordinary-attempt-migration`).
     - 안전 스키마가 없는 레거시 DB는 v2 검사에서 거부되고 아무것도 생성되지 않음을 단언한다(`phase4-open-marker-integrity`).
   - 업그레이드 경로 13개 사례는 `tests/helpers/upgrade-deferred.mjs`의 사유를 달아 보류(skip)한다. 12개는 업그레이드 성공 경로이고, 1개(`phase4-offline-open-upgrade`의 마커 손상 거부)는 업그레이더가 손상 없는 v2 기준 DB도 거부해 거부 원인을 마커 탓으로 판별할 수 없어서 보류했다. Phase 4의 "전체 테스트 통과"는 이 보류분을 빼고 판정한다.
3. **메모리 DB는 지원하지 않는다.**
   - `initDatabase`는 메모리 경로(`:memory:`, `mode=memory`)와 모든 `file:` URI 형태를 명확한 메시지로 거부한다. Windows에서는 `file:x`가 대체 데이터 스트림으로 해석될 수 있기 때문이다.
   - 메모리 모드 테스트 사례는 파일 DB로 바꾸거나 제거했다.
   - 저장소나 스토어 단위 테스트가 `better-sqlite3`의 메모리 DB를 직접 여는 것은 운영 클라이언트를 거치지 않으므로 그대로 허용한다.

4. **연결 정리 실패는 일반 오류로만 보고한다(기존 설계 확인):** `async-writer.ts`는 쓰기 연결을 닫다가 실패하면 원래 close 오류를 버리고 "Writer cleanup failed"만 보고한다. 1차 리뷰는 이를 근거 없는 약화로 보고 `cause` 보존을 요구했다. 그러나 `tests/db-lifecycle-reentrancy-memory`의 "cleanup exceptions do not leak through writer failure or quarantine retry"가 close 오류의 민감 정보가 새지 않아야 한다는 요구를 명시하고 있어서, `cause` 추가는 되돌렸다. `async-writer-startup` 테스트는 원래 close 오류가 포함되지 않음을 단언한다. 그 대가로 close 실패의 진단 정보(원인 메시지)는 남지 않는다. 내부에도 보존하지 않으며, 커밋 후 정리 실패만 일반 문구로 로그에 남는다.
5. **도달할 수 없게 된 메모리 분기:** `async-writer.ts`의 `shared.name === ':memory:'` 공유 연결 분기는 메모리 경로를 `initDatabase`가 거부하므로 운영에서 도달할 수 없다. 가짜 DB를 쓰는 VM 테스트(`db-lifecycle-reentrancy-memory` 등)는 일부 모드에서 아직 이 분기를 통과하므로, 해당 모드는 운영 writer 경로를 검증하지 않는다. 분기 제거(또는 불변식으로 throw)와 VM 테스트의 파일 기반 전환은 BACKLOG에서 추적한다.

## 대안

- **`db:migrate`나 서버 시작이 파일을 자동 생성:** 사용은 편하지만 경로 실수로 빈 DB가 생기는 위험이 되살아난다. 채택하지 않음.
- **신규 설치를 Phase 6까지 미지원:** 서버를 실행할 방법이 없어진다. 채택하지 않음.
- **업그레이드 테스트 전부 보류:** 기존 DB를 보호하는 거부 동작의 회귀 테스트까지 사라진다. 채택하지 않음.
- **Phase 4에서 업그레이드까지 구현:** 작업량이 크고, 스크립트를 켜려면 ADR 0013에 따른 별도 승인이 필요하다. BACKLOG로 미룸.
- **메모리 DB 자동 provision:** 메모리 DB는 항상 새것이라 경로 실수 위험은 없다. 그러나 테스트 편의를 위한 경로가 운영 코드에 들어가고, 연결마다 별개의 DB라 다중 연결 검증에도 쓸 수 없다. 채택하지 않음.

## 결과

- 새로 만든 DB만 쓸 수 있다. 기존 DB의 계정과 기록을 옮기려면 업그레이드 경로를 따로 구현해야 한다(BACKLOG "기존 DB 업그레이드 경로").
- 검증: `tests/phase1-migrate.test.mjs`에서 다음을 확인한다.
  - `db:init`이 새 폴더에 DB를 만들고, 그 DB를 `db:migrate`가 받아들인다.
  - `db:migrate`는 없는 DB를 만들지 않는다.
  - 빈 파일이나 초기화된 파일이 이미 있으면 거부하고, 해시가 바뀌지 않는다.
  - 메모리 DB는 두 명령 모두 거부한다.
- 한계: 상위 폴더를 자동으로 만들기 때문에, `db:init`을 명시적으로 잘못된 경로에 실행하면 그 경로에 새 DB가 생긴다. 실행 시 절대 경로를 출력한다.
