# ADR 0014: 오프라인 전환·복구의 하드링크 확인

## 상태와 배경

작업본의 429 전환 helper와 별도 OPEN 전환·복구 도구에 적용하고 격리 테스트했다. 429 실행 CLI는 여전히 비활성화되어 있으며 Phase 4 완료나 운영 전환 승인이 아니다.

이전 helper는 파일과 각 상위 경로의 링크 여부 및 장치·파일 식별자를 확인했지만 DB 파일 자체의 하드링크 수는 검사하지 않았다. 다른 이름이 보호된 디렉터리 밖에 존재한다면 경로를 보호하더라도 같은 파일에 별도로 접근할 수 있다. Windows 테스트 소유 DB에 두 번째 하드링크를 만든 뒤 기존 helper가 이를 거부하지 않고 전환하는 것을 재현했다.

## 결정

`runOffline429`, OPEN 전환 및 OPEN 복구 도구는 대상 DB의 `nlink`가 정확히 1인 경우만 허용한다. 값이 없거나 확인되지 않아도 거부한다. 각 경로 확인 시 대상 파일의 링크 수를 재확인하고, 열린 읽기 전용 디스크립터의 파일 종류·링크 수·식별자도 SQLite 오픈 전후와 트랜잭션 내부 최종 확인에서 재검사한다. 트랜잭션 중 두 번째 링크가 확인되면 기존 예외 경로를 통해 롤백한다. 일부 파일시스템에서 링크 수를 제공하지 않으면 정상 파일도 거부할 수 있다.

복구 도구의 읽기 전용 `inspect`도 하드링크가 있으면 거부한다. 세 도구 모두 운영 적용은 별도 검토가 필요하다.

## 검증

별도 에이전트가 전달된 코드와 테스트 발췌를 정적으로 검토했다. Windows의 테스트 소유 파일에서 기존 코드의 미거부를 확인한 후 수정했다. 집중 테스트는 외부 1/1·내부 10개를 완료했다. 이 중 실제 하드링크가 이미 있는 DB는 거부됐고, 별도 사례에서 실제 SQLite 트랜잭션이 제한·사용량 데이터를 쓴 뒤 테스트가 링크를 만들자 커밋 전 거부돼 양쪽 이름의 스키마·인덱스 메타데이터·행·저널 모드가 롤백 전과 같았다. 이는 같은 프로세스에서 유도한 경합이다.

별도 OPEN 전환과 복구 CLI도 수정 전 하드링크 대상에 성공하는 문제를 각각 재현한 후 수정했다. 하드링크 거부와 링크 제거 후 정상 전환·정상 복구를 각각 1/1로 확인했다. 복구 테스트는 다른 종류의 OPEN, 기존 제한과 정확한 감사 행을 확인했지만 최소 합성 스키마를 사용했다. 과거 스키마의 별도 프로세스 초기화 회귀 1/1, 기존 429 CLI·사용량 전환 회귀 18/18도 통과했다. 사용한 DB와 링크는 테스트 소유이며 실제 운영 DB는 사용하지 않았다.

## 한계와 운영 전제

확인 사이에 링크가 생성됐다가 제거되거나 마지막 검사 이후 생성되는 상황은 막지 못한다. SQLite는 검사한 파일 디스크립터가 아니라 경로로 별도 핸들을 여므로 동일 파일임을 원자적으로 증명하지 못한다. WAL/SHM의 별칭, 모든 Windows reparse 종류와 상위 경로 교체, 다른 프로세스의 이후 쓰기도 이 검사로 차단되지 않는다. 따라서 DB·WAL·SHM 전체를 보호하는 신뢰 가능한 오프라인 디렉터리와 모든 라우터 및 미해결 작업 중단, 검증된 백업은 여전히 필수다. 링크 수 검사나 운영자 확인을 운영 안전성의 증명으로 취급하지 않는다.
