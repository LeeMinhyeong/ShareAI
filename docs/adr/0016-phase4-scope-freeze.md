# ADR 0016: Phase 4 완료 범위 고정

- 상태: 사용자 승인(2026-11-09). 방향 결정이며 아래 항목은 아직 구현·검증되지 않았다. Phase 4 및 운영 적용은 미승인.
- 관련: [ADR 0005](0005-retry-failover-policy.md), [ADR 0008](0008-new-request-account-429-policy.md), [ADR 0009](0009-shutdown-deadline-database.md)

## 배경

Phase 4 완료 기준 "다중 계정 테스트에서 선택·쿨다운·자동 전환 확인"의 해석이 모호했고, 종료 소유권 작업이 범위를 계속 넓히며 완료 시점이 불분명했다. 코드 정적 확인 결과 `src/upstream/forward-chat.ts`의 120초 타이머는 발송 직전 시작돼 `finally`에서만 해제되므로 스트림 소비와 정산 전체에 적용된다(190·260·353행 부근). 또한 클라이언트 연결 종료(77행)와 120초 시간 초과는 controller abort로 이어지고, 이 경로에서 일반 계정 OPEN 정산 코드를 거치지 않는 것으로 보인다. 이 마지막 관찰은 **정적 읽기이며 재현 테스트로 확인되지 않았다.**

## 결정

Phase 4 완료 범위를 다음 네 항목으로 고정한다. 범위 밖 결함은 별도로 [BACKLOG](../../BACKLOG.md)에 기록하고, 범위 안 데이터 손실·보안·핵심 기능 결함이 새로 발견되면 영향과 함께 사용자에게 보고한다.

1. **자동 전환 = 새 요청 전환.** A의 429/확인된 5xx 이후 새 논리 요청이 적격 B를 선택하는 ADR 0008 방식만 Phase 4 완료 기준으로 삼는다. 같은 요청의 다른 계정 재전송은 ADR 0005에 따라 비활성으로 두고 백로그로 넘긴다. 인수 테스트는 ADR 0008의 검증 항목을 따른다: 같은 격리 파일 DB를 공유하는 라우터 프로세스 둘, 합성 공급자, A의 429 1회 수신, 다른 프로세스의 다음 요청이 B 선택, 재시작 후 제한 유지, 지정 고정 SIWC 비전환.
2. **종료는 핵심 DB 생산자 drain 보장까지.** 모든 DB 사용 경로를 목록화하고 요청 처리·정산·토큰 갱신·SIWC/OAuth 작업의 종료 소유권을 확인한다. ADR 0009의 "정상 drain 후에도 DB를 명시적으로 닫지 않음 + 5초 실패 종료" 정책은 유지한다. 정상 DB close의 전역 증명은 Phase 6(운영)으로 넘긴다.
3. **120초 전체 제한을 첫 응답 제한 + 무응답(idle) 제한으로 대체.** 전체 생성 길이에는 제한을 두지 않거나 큰 상한만 둔다. 구체 값과 적용 경계(401 갱신 재시도, 정산, SIWC)는 구현 시 정하고 이 ADR과 ADR 0005에 반영한다. ADR 0005의 "단조 시계 기준 총 120초 deadline 공유" 결정은 이 항목으로 대체된다.
4. **중단된 OPEN 처리 포함.** 먼저 취소·시간 초과 후 OPEN 잔존을 인증 HTTP 경로 테스트로 재현한다. 재현되면 라우터 스스로 끊은 시도(클라이언트 취소·라우터 시간 초과)에 대해 보수적 대기 후 자동 해제하는 정책을 설계해 ADR 0008을 개정한다. 그 외 불확정 결과(크래시, 응답 유실 등)의 기존 보수적 차단은 별도 근거 없이 완화하지 않는다.

### 항목 3 구체화 (2026-11-09, 구현 시 결정)

- **첫 응답 제한 60초:** 각 dispatch(401 갱신 재시도 포함)마다 공급자 요청 시작부터 응답 헤더 수신까지. 일반 계정과 SIWC 동일.
- **무응답 제한 300초:** 헤더 수신 후 공급자 본문 바이트를 받거나 클라이언트에 쓰기가 끝날 때마다 다시 잰다. 정상적인 긴 생성은 끊지 않는다. 추론 모델이 바이트 없이 300초 넘게 생각하면 끊길 수 있다.
- **전체 길이 제한 없음.** 기존 120초 전체 제한은 제거한다. 시간 초과로 라우터가 끊으면 ADR 0008 개정에 따라 OPEN이 60초 제한으로 전환된다.
- 디스패치 전 승인(admission) 대기와 비정상 응답 뒤 처리(401 갱신 포함)도 첫 응답 제한 값으로 묶는다. 새 dispatch가 다시 건다.
- 본문 바이트 감지는 공급자 응답 본문을 `TransformStream`으로 감싸 청크마다 타이머를 다시 거는 방식이다. 파서가 버리는 SSE 주석(heartbeat)도 진행으로 친다.
- 값은 `forward-chat.ts`의 `INFERENCE_TIMEOUTS` 상수이며 운영자 설정화는 백로그다. 실제 공급자의 heartbeat 간격과 추론 무음 시간은 미검증이다.
- 헤더를 곧바로 보내는 공급자에게 첫 응답 제한은 헤더 지연만 막는다. 헤더 이후 첫 바이트까지는 무응답 제한으로 잰다.
- 디스패치 전 승인 대기 제한은 결정 외 추가 경계다. 헤더까지 최악은 승인 60초 + 첫 응답 60초이고, 401 갱신이면 각각 한 번 더 붙는다.
- 401 갱신이 첫 응답 제한을 넘기면 재시도는 보내지 않는다. 미발송 시도는 정확 해제되고 60초 제한을 받지 않는다. 버려진 갱신도 공유 flight로 끝까지 진행되어 회전 결과가 저장되고, 다음 요청은 재갱신 없이 새 토큰을 쓴다(테스트로 확인).
- 디스패치 직전 중단 확인: `withAsyncWriter`는 매 시도마다 `signal.throwIfAborted()` 직후 `BEGIN IMMEDIATE`(timeout 0)를 실행하고, 잠금이 바쁘면 abort 리스너를 단 비동기 재시도를 한다. fence 콜백(검증→확인→`start()`)은 BEGIN 뒤 같은 동기 구간에서 실행되므로, writer 자신의 확인과 fence의 확인 사이에는 중단이 끼어들 수 없다. fence 확인 단독 제거는 동치 변형이다(파일 DB 경로 기준; 메모리 경로도 같은 트랜잭션 안에서 동기 확인). 같은 signal이 writer와 fence에 전달되고, `controller.abort()`는 소켓 `close`와 타이머 콜백에서만 비동기로 호출된다. fence 확인은 방어 심층으로 유지하며 전용 테스트는 없다. 잠금 대기 중 타이머 발화는 별도 테스트(워커 스레드가 쓰기 잠금 보유)로 확인한다.
- 어느 제한이 발화했는지는 실패 로그의 `routerTimeout`에만 남긴다. 정산 판정은 `signal.aborted`만 본다.
- 검증: `tests/phase4-inference-timeouts.test.mjs` 12개 사례(축소 값 800ms/2400ms, 구 전체 제한 가로채기 3200ms, 경과는 합성 fetch 호출부터, idle 상한은 구 전체 제한 미만). 변형 10개 중 9개 검출(쓰기 잠금 대기 사례가 승인 대기 제한 제거를 검출). fence 확인 단독 제거는 위 이유로 동치 변형이다. SIWC 승인 대기 제한과 클라이언트 쓰기 후 재설정은 직접 검출되지 않는다(BACKLOG).

## 대안

- 같은 요청 재전송 포함: 공급자별 실행 전 거절 근거가 없고 중복 실행·과금·정책 위험이 있어 Phase 4에서 제외.
- 정상 DB close까지 Phase 4 포함: 전체 생산자 증명이 필요해 범위가 계속 확장되므로 Phase 6으로 이연.
- 120초 전체 제한 유지: 정상적인 긴 생성이 끊기고(4번과 결합 시) 계정이 막힐 수 있어 기각.
- 중단 OPEN 현행 유지: 취소 한 번으로 계정이 사실상 영구 차단될 수 있어 기각(재현 전 가정).

## 결과

- 사용자에게 A가 막히는 순간 요청 하나는 429로 실패할 수 있다. 클라이언트 자체 재시도 여부는 미확인이다.
- 커밋된 데이터는 WAL 모드에서 close 없이 종료돼도 다음 open 시 복구되는 SQLite 표준 동작에 의존한다. 추적되지 않은 작업은 종료 때 끊길 수 있다.
- OPEN 자동 해제는 ADR 0008의 "OPEN 무기한 유지"를 일부 완화하므로, 동시 발송 방지와 429 관찰 누락 위험을 개정 ADR에서 명시해야 한다.
- 이 ADR은 방향 결정일 뿐 구현·리뷰·테스트 완료를 뜻하지 않는다.
