# ADR 0006: Shared cooldown, in-flight fencing, and uncertain results

**Status: PROPOSED — NOT IMPLEMENTED.** Adoption requires implementation, independent review and the proof tests below. This is a design for Phase 4, not a claim that the present router provides distributed cooldown safety. Related: ADR 0002 (access), 0003 (SIWC logout), 0004 (account reservations), 0005 (retry/failover).

**Superseded policy assumption:** The user subsequently chose to allow a *new* logical request to select another account when a 429's scope is unknown. The global-blocking default below is therefore not an approved product policy. It does not establish that provider restrictions are account-scoped or that such use is permitted. Same-request replay remains a separate decision. See ADR 0008 when available.

## Context: actual working tree

- `src/account-pool/manager.ts` keeps ordinary and SIWC cooldowns in separate process-local maps; `getCandidates`/`selectCandidate` filter them, but another process or restart cannot see them. The SIWC object marker prevents some stale successes only within one process. Ordinary `recordSuccessAsync` resets local state after a writer returns. `recordFailureAsync` commits account status first and then updates the local map. `state_revision` changes can also replace the local state. These do not form an authoritative shared cooldown.
- `src/upstream/forward-chat.ts` selects before dispatch. Ordinary `invokeAccountAttempt` in `account-quota.ts` commits a UTC daily charge, then reacquires `withAsyncWriter`, revalidates and calls `start()` synchronously inside the fence. SIWC separately rechecks ACL, snapshot/revision and local cooldown inside its writer before starting. The ordinary account selection path does not currently filter by user; do not infer an ordinary-account ACL that does not exist. SIWC's policy and logout checks must remain intact.
- `forward-chat.ts` emits non-streaming success and streaming role/data before recording success; on ordinary failure it sends an error before `recordFailureAsync`, and skips recording on abort. An SSE error can occur after output has started. `inference.ts` discards HTTP error bodies, retains headers in `UpstreamError`, and may discover the SIWC limit in a later SSE event. Neither an HTTP 200 nor output means the final result is known. Existing same-account 401 refresh/reinvoke needs separate ADR 0005 reconciliation.
- `src/db/async-writer.ts` opens a file-backed zero-busy-timeout connection, uses synchronous `BEGIN IMMEDIATE` callbacks, asynchronous bounded acquisition retries and `synchronous=FULL`; it does not repeat callbacks or uncertain commits. `src/db/client.ts` initializes WAL and FULL, but its shared connection uses a 5000 ms timeout. Do not assume every DB path is event-loop nonblocking. ADR 0004's daily quota is separate from usage display logs and is consumed even when dispatch is prevented after reservation. `tests/phase4-durable-restriction-red.test.mjs` specifies that an unknown 429 must survive restart and block bypass through another account; it is a proposed regression target, not evidence that it passes.

## Decision proposed: scope, not blanket account switching

A physical attempt may start only when no active restriction **or unresolved potentially affecting attempt** intersects its conservative impact envelope. Candidate ordering is advisory; the database writer is authoritative. Scope keys are canonical, server-defined internal IDs, never user-provided URLs or secret material. The model must support provider, endpoint family, billing/organization identity when actually known, `(kind, account_id)` and, only where documented, narrower model/resource identities. An intersection exists if scopes might overlap, not merely if strings match; absent, ambiguous or conflicting identity is a wildcard. `upstream` and `siwc` account IDs are distinct namespaces, but that does not prove their upstream billing scopes are distinct.

**Safe default envelope:** all inference endpoints and accounts of the same provider, including SIWC and ordinary credentials; unknown 429 restricts this entire envelope. This is a deployment assumption, not proof that providers are independent: if providers share a gateway, organization-level limiter, proxy or other plausible common limit, configure their common **global/domain envelope** instead. If no defensible boundary is known, use a global envelope. Do not treat different credentials, endpoint paths, models or users as evidence of independence. The default permits new requests to demonstrably separate providers/domains while one domain is blocked. Until a narrower boundary is proven, only one unresolved attempt per intersecting envelope may be in flight: without this admission rule an already-started concurrent attempt could receive an unknown 429 while another is dispatched before that response is recorded. This throughput/availability cost is intentional. It cannot retract calls that began before a limitation arose externally.

A versioned administrator policy may enable a narrower envelope and known-scope classification only for a documented provider+endpoint+credential/billing boundary and exact, verified response signature; record evidence/version and negative tests. Unknown/malformed signatures always widen to the configured conservative domain, never fall back to account. Narrow concurrency is safe only if the evidence covers **all** restrictions that an attempt can report, including late SSE failures and uncertain outcomes; a single documented account-specific signature alone is insufficient. If an unexpected broader restriction can still appear, retain broad admission serialization. A provider-wide or unknown 429 blocks new intersecting requests, not just automatic retry. A known account-scoped restriction blocks only that proven scope; unrelated eligible accounts/users may start new logical requests. No automatic replay or cross-account retry is authorized by this ADR; ADR 0005 governs those separately. The existing 401 retry must not bypass the ledger or silently be treated as approved.

Admin-configured, audited non-limit switches (e.g. explicitly enable/disable a provider integration, account, or non-limit circuit-breaker for documented operational failures) may control new selection when authorized; they must not disable quota, bypass an active 429/unknown restriction, or transform uncertainty into proof of non-execution. Any more permissive interpretation requires a separate decision and provider evidence. No reset hint alone licenses switching billing paths.

## Durable model and invariants

Add additive, transactionally migrated tables; final names/DDL are implementation work:

1. `attempts`: immutable random `attempt_id` PK, logical request ID + attempt ordinal unique, actor/user internal ID, `(kind,id)`, provider, endpoint family, impact-domain/policy version, credential and authorization snapshots/generations, account quota reservation reference/day, created time, result state and monotonic revision. Store a canonical immutable scope snapshot. No token, header, request/response body or prompt. Foreign-key/tombstone policy must preserve unresolved and audit records if accounts are removed; never cascade away a safety fence.
2. `restrictions`: restriction ID, canonical scope/type, source attempt, generation/sequence, reason enum and sanitized evidence reference, `until` only if justified, and active/resolved state. Multiple independent restrictions coexist; compute intersection across all active rows. An uncertain attempt itself is an implicit active restriction covering its immutable impact envelope, not a timer-based lease. Indices cover domain/state and attempt ID; uniqueness constraints prevent double finalization. Invalid/missing schema, state or clock => fail closed.
3. `resolution_audit`: append-only actor, timestamp, scope, exact attempt/restriction IDs and revisions, sanitized justification/evidence reference, action and result. `policy`/generation rows version identity mappings and administrative changes. Exact physical schema and migration of account/ACL revisions are open implementation details; mutation sites must be inventoried and covered before enforcement.

States: `OPEN` means committed pre-dispatch and potentially sent, including crashes before the actual call; `FINISHED_SUCCESS`, `FINISHED_FAILURE`, `NOT_SENT` (only with positive local proof under the dispatch fence), and `RECOVERED` are terminal. A unique attempt ID is never re-dispatched. A successful stream becomes final only after valid complete consumption; failures and uncertainty are finalized or remain OPEN. Finishing is idempotent: inside one writer compare `OPEN` plus immutable attempt revision, atomically insert/extend all restrictions and set the terminal result. A duplicate with exactly the same outcome returns the already committed result; a conflicting or stale finish cannot alter it. If commit acknowledgement is uncertain, read back by ID; if still uncertain leave its scope blocked and do not send/retry. Never record an actual failure as success or NOT_SENT.

**Ordering invariants**

- The ledger OPEN row and ordinary daily quota charge commit together before any possible network call. Do not reserve twice: refactor ADR 0004's transaction, preserving its day, migration ambiguity, unlimited-account accounting and no-refund semantics. SIWC gets a ledger row but no invented ordinary account quota. User daily quota remains one charge per logical request. Prevent internal HTTP retries/redirect replay or account for every physical call separately.
- Between that commit and dispatch, OPEN fences all intersecting attempts, including a different account/process. The owning attempt is excluded from its own check, but no other one is. If OPEN is committed and no call occurs, it stays conservatively fenced until a positively proven NOT_SENT transition or manual recovery. No use of SQLite rollback as evidence that a separately initiated fetch was unsent.
- A short second `BEGIN IMMEDIATE` checks the exact committed attempt, all intersecting restrictions/other OPEN rows, current policy version and envelope, user enabled/key validity, applicable share ACL, account enabled, capability/model compatibility, credential generation/refresh intent, quota day and cancellation. Call `start()` **synchronously under that writer** after all checks and return its promise wrapped in a non-Promise container; never await network under lock. This serializes initiation with logout, ACL, policy and administrative restrictions using the same DB writer. A fetch may leave even if this second transaction fails/commit acknowledgement is lost: keep OPEN, consume the promise safely, and do not resend. Do not retry the callback. Do not set NOT_SENT if `start()` was entered, threw ambiguously, or if a post-start transaction failed.
- Authorization changes after initiation cannot retract a request. Logout/re-login/credential refresh must advance durable generations under the same writer. Separate **credential generation** from persistent upstream identity/scope: relogin does not erase provider, domain, billing or unresolved old-attempt restrictions. An old result may never mutate a new credential's account status or clear a new restriction, but a late 429 still installs its conservative old envelope restriction even after logout/relogin. If identity mapping is unknown or changed, widen rather than silently drop the result.
- Success does not clear active restrictions at all. Expiry or authorized recovery is the only removal mechanism; backoff counters may be reset only by a CAS tied to the generation observed at dispatch and must not shorten any active restriction. `max(existing_until, new_until)` applies only to the same exact scope/reason with comparable valid TTLs; never overwrite a broader or indefinite restriction with a narrower or timed one. Policy changes and reset use writer-serialized compare-and-swap on exact restriction/attempt revision, plus an audit row; an older in-flight result cannot undo them. A late failure after a reset creates a fresh restriction, including when it belongs to an old generation. Recovery cannot declare an actively running attempt safe merely because its owner is slow.

## Protocol sketch

```text
prepare physical attempt:
  choose eligible candidate (advisory, no output/retry promise)
  await writer(deadline, cancel):
    validate current auth, ACL, generation, scope-policy and compatibility
    reject if any intersecting OPEN or active restriction
    reserve ordinary account's UTC daily attempt exactly once if applicable
    INSERT OPEN(attemptId, requestId, ordinal, immutable scope + revisions)
  # commit confirmed before any fetch; unknown commit => no fetch, inspect by ID

initiate:
  await writer(deadline, cancel):
    verify own OPEN; recheck all gates, other OPEN and restrictions
    # synchronous only, do not await; mark local enteredStart BEFORE calling
    enteredStart = true; pending = start(); return { pending }
  await pending and consume upstream (including SSE terminal event)

finish(outcome):
  await independent bounded writer (not the cancelled client signal):
    if exact terminal result exists return it; conflicting result => alert/block
    if OPEN: classify with versioned evidence; insert restrictions if needed;
             CAS OPEN -> terminal atomically
  # only after confirmed finish: send 429/error if not yet committed
  # after client headers/bytes: cannot retract; persist before emitting error frame,
  # otherwise close connection, leaving OPEN blocking until recovery
```

Before starting, a validation failure can transition OPEN to NOT_SENT under the writer only if `start` has provably never been entered and commit is confirmed; retaining OPEN instead is safe. A crash at any point, client disconnect, timeout, ambiguous fetch error, streaming truncation, or failed result write is not proof of no upstream effect. Attempt finalization needs its own bounded cancellation-independent deadline; if it cannot commit, close/503 if possible and leave OPEN. Do not send the upstream 429 as if recorded. For a streaming response already committed, emitted output cannot be recalled; stop output and close if the required failure record cannot be confirmed. Before emitting an SSE error frame, finish and restriction must be confirmed. A finish failure after a success response likewise leaves OPEN; the design should finalize non-streaming success before `res.json` and streaming success before final DONE where feasible. Already emitted partial data remains real and never authorizes replay. OPEN remains blocking during the entire stream. 401 refresh or any future physical resend requires a distinct new durable attempt and ADR 0005's independent authorization.

## TTL, recovery, retention, and operations

**Current implementation limitation:** Ordinary-account 429 expiry uses the local wall clock and does not detect forward or backward clock jumps. A forward jump after recording a deadline can expire it prematurely; this remains unresolved and is not fixed by comparing provider and local dates. Deployments need a trustworthy clock and operator reconciliation after clock anomalies.

For a documented, trustworthy account-scoped 429 with a valid reset or bounded retry hint, persist an absolute UTC `until` with evidence and never choose an earlier time than a trustworthy provider hint. If the hint is absent/invalid or scope is unknown, default to **indefinite until explicit recovery**, not a fabricated expiry. A locally configured backoff may extend a known restriction; it cannot shorten a provider limit or make unknown scope safe. All processes read authoritative SQLite at dispatch, including after restart; no process-local cache may override it. Expiration is effective only under a trusted shared wall clock and when the rule permits automatic expiry. Clock rollback, unacceptable skew or invalid timestamp blocks affected domains and alerts; monotonic deadlines are for local waiting only. FULL/WAL durability depends on the filesystem and hardware honoring sync; SQLite is not a multi-host consensus database. Require all participating processes on a supported single-host shared DB/locking boundary, no stale replicas or old binaries, and document/test storage and clock assumptions. Distributed hosts need a separately designed linearizable coordinator.

OPEN never expires or replays automatically, even after restart or an account replacement. Admin recovery is a distinct authenticated, authorized operation showing a redacted list of exact attempt/restriction IDs, scope, age, generation and uncertainty. To recover an OPEN row, first drain/fence all potentially owning processes and prevent any delayed response or ongoing provider execution from being mistaken for completed; inspect available provider evidence and explicitly accept residual uncertainty. In one writer CAS the exact revisions, mark RECOVERED and append the actor/reason/evidence reference; reject stale views or changed policy. Recovery is an operator risk decision, not proof of remote non-execution, and must not grant automatic replay of the original logical request. Clearing a confirmed provider restriction additionally requires evidence of expiry/lift or an explicitly authorized exception with documented provider policy. Re-login/logout and ordinary reset never automatically clear either. A live process receiving a result after recovery must not mutate a newer credential or clear state, and must be able to append a new broad restriction for a late 429; recovery therefore requires process drain/fencing as well as CAS.

Keep OPEN and unresolved restrictions indefinitely; never delete them for age, quota rollover, account deletion or backup restore. Keep terminal attempts and recovery audit at least **90 days** after terminalization, and longer whenever referenced by a live restriction, incident hold, unresolved audit or policy/legal retention; prune only resolved unreferenced rows transactionally, leaving necessary tombstones/unique request-attempt IDs for the deduplication horizon (at least 90 days). This is an operational proposal, not a compliance claim. Backups must include WAL consistently; restore can resurrect stale state or lose newer fences, so stop all writers and require operator reconciliation with the interval since backup before enabling any domain. Alert on stale OPEN, blocked domains, write contention, invalid clocks and disk-full without exposing secrets.

Error output preserves only approved provider status/code and safe retry guidance; no raw response body, tokens, prompt, headers, or credentials in ledger, logs, admin UI or evidence. ACL checks precede disclosure; missing and unauthorized explicit SIWC IDs remain indistinguishable. Admin endpoints require existing admin authentication plus explicit authorization, audit, CSRF protection where applicable, and sanitized evidence. Sharing multiple accounts does not override provider terms.

## Failure and race matrix

| Event | Required behavior / remaining uncertainty |
|---|---|
| Selection races restriction, ACL, disable or credential change | Dispatch writer rechecks authoritative rows/generations; reject, no network. No reliance on map or stale candidate. |
| OPEN commit fails or acknowledgement unknown | Do not start; read exact ID; block if uncertain. No retry of callback/charge. |
| Crash after OPEN commit but before start | OPEN blocks envelope indefinitely; conservative false positive; no replay. |
| Crash/disk error after start, or dispatch transaction rollback/unknown commit | OPEN already durable; treat as possibly sent; never infer unsent from rollback. |
| Concurrent process attempts same envelope | Unique and intersection check inside writer permits at most one OPEN; unrelated proven domains continue. |
| 429 arrives before durable finish; another request races | OPEN blocks intersecting dispatch while classifier/finalizer runs; atomically replace fence with restriction, no gap. |
| Unknown 429; missing/invalid headers or untrusted signature | Indefinite domain-wide restriction; unknown cross-provider boundary widens to global. No invented TTL. |
| Proven account-scoped 429 / known valid reset | Install only proven scope with safe expiry; unrelated scopes can proceed only if their admission envelopes are proven nonintersecting. |
| Valid 429 with malformed or conflicting TTL | Indefinite or later verified time; never clear early. |
| Concurrent old success after newer failure/reset | Success never clears restrictions; exact CAS prevents stale overwrite. Late failure installs new restriction. |
| Logout/relogin/refresh races dispatch or result | Shared writer establishes order; old credentials cannot start after revocation, nor update new credential; broad old 429 persists. Already sent call cannot be retracted. |
| Timeout, disconnect, network loss, process death | Do not retry; OPEN remains unless a confirmed finish conservatively installs appropriate uncertainty restriction. Cancellation does not cancel remote execution. |
| DB busy, disk full, finalization timeout or uncertain commit | Bounded async lock acquisition; no new dispatch in affected envelope. Read back exact ID when possible, otherwise retain OPEN; no acknowledged error frame before finish. |
| SSE 429 after role/data; finish write fails | Bytes already sent remain; close without misleading success/error frame; OPEN blocks. If finish commits, emit appropriate sanitized error or close. |
| Restart, multiple processes, daily rollover | Same file and schema see OPEN/restrictions; quota day roll must not clear either. |
| Admin reset/recovery races result or policy edit | Drain/fence where necessary, CAS exact revisions and audit; result may create new restriction, never silently erase one. |
| Corruption, bad scope mapping, unknown schema, clock skew, restore | Fail closed for affected domain or global if unknown; alert, reconcile; do not assume empty state. |
| Old binary, bypass path, hidden redirect/SDK retry | Unsafe mixed deployment; offline cutover and exhaustive call-site inventory required, prohibit bypass before enabling. |

## Delivery and proof gates

1. **First safe vertical slice:** behind an off-by-default flag, integrate one ordinary API-key inference path end-to-end with global/domain-serialized OPEN, ADR 0004 atomic quota reservation, fenced `fetch`, unknown HTTP 429 => indefinite durable domain restriction, failure-before-response finalization, success completion, admin read/recovery, and safe restart. Other production paths remain on old behavior; do not claim shared safety or turn on mixed-path production enforcement. A real deployment must either fence/disable every bypass including SIWC and OAuth paths or wait for phase 2. Include mock-file-backed multiprocess tests for reservation-before-start, held response vs second process, two accounts, failure-before-response, crash at each boundary, restart, writer contention, uncertain commit and explicit recovery. Verify non-429 and output/cancellation cases too. No actual provider credentials or service calls.
2. Extend the same authoritative gate to all ordinary OAuth/refresh/401, SIWC ACL/logout/relogin, HTTP and late SSE paths; integrate user quota and disable direct bypasses. Add proven narrower scopes only with provider evidence; preserve availability across demonstrated nonintersecting domains. Handle legacy callers (`updateAccountStatus` etc.) and administrator mutation paths, including every way identities or policy can change.
3. Offline cutover: drain and stop **all** old binaries and writers; consistent verified backup; additive transactional migration with schema/version checks; start only fenced binaries with one supported shared DB. Simulate rollback/restore and reconciled migration, document monitoring and recovery. No mixed-version safety claim.
4. Independently review and run focused isolated mock tests for matrix rows, full stream lifecycle, ACL/key revocation, logout/relogin, TTL/clock, duplicate/conflicting finishes, policy reset races, process kill/restart, at-least-once finish, secret redaction and ordinary/SIWC quota invariants. Verify no request reaches mock upstream while an intersecting restriction/OPEN exists; test an unrelated domain remains usable. Validate event-loop responsiveness under a held SQLite writer. Run broader suites only where safely isolated and practical; do not assert unrun tests pass.

## Open decisions and limits

- Provider-specific contracts, exact scope evidence, safe endpoint/billing-domain mapping, duration and whether any two credentials or providers truly have independent limits remain unverified. Start global when provider isolation cannot be justified. 429 classifications in external projects are not proof of provider permission or scope.
- Set deployment-specific clock-skew threshold, admin recovery authority/evidence, retention beyond the proposed minimum, exact handling of an operator accepting uncertain ongoing execution, and any audited non-limit switches. Independent security and product review is required before making recovery available.
- SQLite/filesystem power-loss behavior, supported deployment topology, migration compatibility and nonblocking behavior on every existing DB path need proof. This design cannot give remote exactly-once or atomically combine an external request with a SQLite commit; it deliberately trades throughput and recovery effort for conservative local fencing.
- Cross-provider correctness and actual provider policies are not established. ADR 0005's retry rules are proposed and the currently implemented 401 retry is not automatically compliant. Only claim adoption after proof tests and review.
