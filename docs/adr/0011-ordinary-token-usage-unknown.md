# ADR 0011: Ordinary-account unknown token usage

Status: partial implementation; not production-ready. A staged combined offline migration exists but its executable remains hard-disabled pending independent review and explicit authorization. Startup rejects the legacy `usage_logs` definition before its WAL change. The preflight is rechecked inside the initialization transaction, but the existing WAL-before-transaction sequence cannot eliminate a concurrent schema-change race.

## Problem

The inference parser emits token usage only when both counts are valid; missing, partial or ambiguous usage is unknown, while a reported pair of zeros is known. Before this partial implementation, `forward-chat.ts` replaced unknown with `(0, 0)` on both success and failure. Legacy ordinary `usage_logs` columns are `NOT NULL DEFAULT 0`, so simply forwarding null would fail to persist the log on existing databases. SIWC logs already allow null. Existing ordinary zero values cannot be classified retrospectively as known or unknown.

`UsageLog` permits null and admin log responses pass the fields through. Today's aggregate queries return zero when their SQL sum is null; thus even nullable individual records alone would not distinguish an unknown aggregate from a known zero. The dashboard Stats page defines numeric log fields but currently only renders account counts, not these token fields. External consumers and direct SQL queries may still rely on numbers.

## Proposed direction

Use nullable token columns for new ordinary logs, including failure logs, and preserve the parser's all-or-nothing invariant: both counts are nonnegative safe integers, or both are null. Do not reinterpret legacy zeroes as measured: retain the legacy rows and explicitly describe their values as historically ambiguous. A safe transition for existing databases requires a tested transactional table rebuild that preserves rows, indexes, foreign keys, triggers and application-specific schema objects, detects unsupported schema collisions before modifying the database, and fails closed without changing journal mode on rejected migration. A side table or negative sentinel does not by itself meet the no-fake-zero and backward-compatible direct-SQL requirements.

Expose aggregate completeness separately from the sum of known counts, with a documented compatibility contract; do not label a partial sum as a complete total. Review API consumers before changing response fields or types. Per-log admin responses should expose null for unknown and zero for measured zero. Existing legacy zeros remain indistinguishable without external evidence. Determine explicit behavior for no requests versus requests with unknown usage.

## Implemented compatibility contract

New ordinary rows record `usage_known=1` for a valid pair and `0` for a null pair. A null marker denotes historical provenance, including writes by older binaries; it must never be promoted to known. Legacy zero pairs remain historically ambiguous: per-log `usageKnown` is false even if their numeric values are zero. Per-log unsafe or invalid pairs are returned as nulls with `usageKnown=false`, without rounding SQLite integers. The numeric aggregate remains a bounded sum of valid numeric pairs, including historically ambiguous values for compatibility; `totalTokensComplete` is false if any included row has unknown, invalid, or historically ambiguous usage, or if the sum exceeds the safe integer range. No rows gives zero and complete true. Completeness applies only to currently persisted qualifying rows: dispatches whose best-effort log write fails are excluded, so it does not establish completeness over all requests. Existing dashboard stats does not render token fields. This contract requires further real-route and streaming verification before production.

## Staged offline migration boundaries

The recognized legacy usage table and indexes correspond to the baseline at `740df936887f40efc727a24b159064bfd4db34e5`; unrecognized schema is refused. Non-integer legacy token storage is unsupported and fails closed rather than being converted; preserve the original database and seek a separately reviewed recovery. The migration keeps historical integer counts and sets their provenance marker to null. It validates both target schemas and foreign keys again before the path recheck and commit. A confirmed commit followed by cleanup failure is not a safe retry: inspect the handles and database. If the transaction throws, including around commit, its outcome may be uncertain. Both database and descriptor cleanup are attempted; a returned close is not proof of SQLite closure unless the handle reports closed.

Current synthetic tests use independently owned in-memory SQLite and fake filesystem adapters, with simplified parent tables and valid usage foreign keys. They compare specified schema, usage, legacy cooldown and OPEN rows, and the in-memory connection's journal mode after injected rollback. These comparisons do not establish byte-for-byte file preservation, persistent journal behavior, power-loss durability, real filesystem identity, or an old-binary fence. The operational design still requires a verified backup, stopped routers and outstanding work, verified legacy provenance, and a trusted single-host directory; path checks cannot eliminate replacement, ancestor or hard-link races.

## Required verification before implementation or deployment

Exercise the real parser, forward success and error paths, and production repository writer against an independently owned in-memory SQLite connection using synthetic provider responses: known nonzero, known zero, absent, partial and invalid usage, with streaming and non-streaming success and errors. Verify persisted rows and externally observable API/aggregate semantics, including mixed known and unknown records. Separately test migration and rollback on synthetic legacy databases initialized through the real schema, preserving rows, schema objects, integrity, foreign keys and persistent journal mode; cover supported variations and collision failures. No operational database should be used as a migration fixture. Validate compatibility with dashboard and external consumers before rollout.
