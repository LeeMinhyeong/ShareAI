# ADR 0021: 계정당 동시 요청 한도와 사용자 취소 시 즉시 반납

- 상태: **사용자 승인 (2026-11-13 결정 1A·2Z·3·4·5), 구현 중 (2026-11-14).**
- 관련: [ADR 0004](0004-account-quota-reservations.md), [ADR 0008](0008-new-request-account-429-policy.md), [ADR 0016](0016-phase4-scope-freeze.md) 4번, [ADR 0019](0019-phase5-client-compatibility-scope.md) 8번

## 배경

- 실사용 목표: 약 10명이 서버 1대·프로세스 1개로 쓴다. 테스트 계정은 Claude 구독 6개, Codex 구독 6개, OpenAI API 키 1개다.
- 지금은 계정 하나에 진행 중인 요청(OPEN)이 하나만 있을 수 있다. OPEN 표(`ordinary_account_attempts`)의 기본 키가 계정 ID다.
  - 계정을 잡는 단위는 사람이 아니라 요청 하나이고, 응답이 끝날 때까지(스트리밍 동안) 잡는다.
  - Codex CLI는 요청을 동시에 두 개 보낸다(실제 확인). 그러면 계정 하나에서 둘째 요청은 다른 계정으로 가거나 실패한다.
  - 10명이 동시에 쓰면 구독 계정 6개가 금방 다 차서 "잠시 뒤 재시도"(ADR 0019 8번)가 자주 난다.
- 사용자가 응답을 끊으면(Esc, 창 닫기) 계정 전체가 60초 쉰다(ADR 0016 4번 → ADR 0008 개정). 사람이 많을수록 계정이 자주 빠진다.

## 결정

1. **계정마다 동시 한도를 둔다 (1A).**
   - `upstream_accounts.max_concurrency`, 정수 1~16, 기본 1. 기본값 1은 지금 동작과 같다.
   - 관리자가 계정별로 올린다(`POST`/`PATCH /admin/accounts`의 `maxConcurrency`, `scripts/phase5-verify.mjs concurrency <id> <n>`).
   - 제안 초기값: 구독 계정 2. 공급자 429를 보며 올린다. 구독 6개씩이면 Claude와 Codex가 각각 동시 12개를 받는다.
   - 한도는 발송 직전 writer 울타리 안에서 판정한다. 그 계정의 OPEN 수가 한도 이상이면 자리를 잡지 않는다. 선택(조언용)도 같은 규칙으로 꽉 찬 계정을 거른다.
2. **사용자가 끊은 요청은 자리를 즉시 반납한다 (2Z).**
   - 클라이언트 연결이 끊겨서 라우터가 요청을 중단한 경우, 그 시도의 OPEN을 지우기만 하고 계정 제한은 걸지 않는다.
   - 공급자 쪽 문제는 지금처럼 계정 전체를 쉬게 한다. 라우터 시간 초과(첫 응답 60초, 무응답 300초), 네트워크 실패, 깨진 응답, 429, 5xx가 여기에 해당한다(ADR 0008).
   - 판정: 컨트롤러가 이미 중단돼 있지 않은 상태에서 응답 연결이 닫혔고, 라우터 타이머가 발동하지 않았을 때만 사용자 취소로 본다. 오류 처리에 들어간 시점에 이미 중단돼 있어야 한다(공급자 실패가 먼저 처리되면 공급자 문제로 남는다).
   - 공급자 실패를 이미 본 경우(리뷰 확인, 2026-11-14): 429·5xx 등 실패 상태 헤더는 본문을 읽기 전에 정산하면서 제한을 건다. 스트림 안의 공급자 실패 이벤트도 사용자 취소 판정과 무관한 별도 분기에서 먼저 정산한다. 그 뒤에 연결이 끊겨도 제한은 그대로다.
   - 라우터가 스스로 응답을 닫는 경로(오류 응답 중 `res.destroy()`)는 모두 위 판정 시점 뒤에 있다. 종료 시한 초과는 연결을 닫고 곧바로 프로세스를 끝내므로 정산 자체가 없다(OPEN 유지).
3. **범위: 일반 계정(`upstream_accounts`)만.** SIWC 계정은 계정당 1개를 유지하고, 사용자 취소도 지금처럼 60초 제한이다(BACKLOG).
4. **새 DB만 지원한다.**
   - OPEN 표의 기본 키를 시도 ID로 바꾼다: `ordinary_account_attempts(account_id TEXT NOT NULL, attempt_id TEXT NOT NULL PRIMARY KEY)`. 안전 표식 버전은 2다.
   - 예전 형식(표식 1)의 DB는 기동을 거부하고, 새 DB를 만들라고 안내한다(`npm run db:init`). 예전 DB를 옮기는 도구는 만들지 않는다.
   - 기존 오프라인 업그레이드·복구 도구(`scripts/offline-*.mjs`, `src/db/experimental-*`)는 표식 1 형식까지만 다룬다. 그 결과물은 이 버전에서 기동하지 않는다.
5. **사용자별 동시 한도는 하지 않는다 (BACKLOG).** 지금 있는 사용자별 한도는 하루 요청 수뿐이다.

## 그대로인 것

- 429 v2 제한은 계정 단위다. 한 시도가 계정을 쉬게 하면 새 요청은 막히지만, 이미 진행 중인 다른 시도는 계속된다.
- 일일 할당량은 시도마다 하나씩 예약한다(ADR 0004).
- 선택 전략(priority, least_used, round_robin)은 그대로다. 빈 자리가 있는 계정 중에서 고른다. priority는 우선 계정이 다 찰 때까지 그 계정에 몰린다.
- 결과를 모르는 시도(발송 결과를 못 봄, 정산 실패 등)는 지금처럼 OPEN으로 남아 자리 하나를 계속 차지한다.

## 받아들인 위험

- 사용자가 끊은 요청을 공급자가 계속 처리하고 있을 수 있다. 그 자리를 바로 다른 요청이 쓰면, 공급자 쪽 실제 동시 처리 수가 잠깐 한도를 넘는다. 공급자가 연결이 끊기면 생성을 멈추는지는 공식 근거가 없다.
- 라우터 앞에 역방향 프록시를 두면, 프록시의 읽기 시간 초과로 끊긴 연결도 사용자 취소로 보인다. 프록시의 시간 초과는 라우터의 첫 응답(60초)·무응답(300초) 시간보다 길게 둔다.
- 구독 계정의 공급자 쪽 동시 한도는 공개돼 있지 않다. 한도를 올려서 429가 늘면 내린다.
- 같은 계정에서 동시에 여러 요청이 나가므로, 계정 공유가 공급자에게 더 잘 드러날 수 있다(Anthropic 약관상 구독 공유는 비허용, README 참고).

## 확인 방법

- 자동 테스트: 한도 1·2·3에서 동시 발송 수, 꽉 찬 계정 건너뛰기, 사용자 취소 시 즉시 반납과 제한 없음, 라우터 시간 초과·공급자 실패 시 기존 60초 제한, 예전 DB 기동 거부, 관리자 설정 검증.
- 실제 확인: 구독 계정 한도 2로 두 사람이 동시에 쓰고, Codex CLI의 동시 요청 두 개가 한 계정에서 처리되는지 사용 기록으로 본다.
