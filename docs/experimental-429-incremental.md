# Experimental incremental 429 prototype (v2 fixture only)

This is an isolated synthetic-file experiment. It is not wired to routing, admission, a scheduler, providers, or any migration, and must not be used on an application database. `fixtureSchema` is exclusively for pre-created disposable test databases. It is not a public migration. A separate independent safety review is required before considering any integration.

## Trust boundary

All modifications must occur through a trusted writer enforcing these same invariants, with SQLite constraints enabled on an intact UTF-8 database. Direct SQL (other than initial trusted fixture setup), arbitrary file corruption, malicious triggers, database/VM snapshot rollback, and non-monotonic clocks are outside the guarantee. The prototype rejects an unexpected schema, marker, counter, or selected malformed row, but deliberately does **not** scan every row: corruption of a different row does not block a valid target. Index membership relies on that trust boundary, including constraints; a corrupted duration may hide from discovery. The schema SQL is compared exactly to the fixture definition; this is not a general SQLite schema equivalence checker.

Every operation opens its own top-level SQLite IMMEDIATE writer and revalidates the marker and schema. Keys are literal, not normalized, and limited to 512 UTF-8 bytes; IDs reject NUL and invalid surrogate sequences. Row validation includes raw UTF-8 byte round-trip and generation at most the counter. Arming increments the generation and keeps the longer duration, or indefinite. `check` starts observing only an already committed generation while holding the writer; it conditionally deletes only after a local monotonic interval. A new instance waits the full interval again. A busy writer can be retried without losing the old observation; indefinite entries are never removed. These properties have not yet been subjected to the full multiprocess crash, contention and injected-write-failure test matrix.

`page(size,cursor)` reads at most 100 finite candidates through a partial keyset index. The caller must save the returned cursor and restart at the beginning after an empty/short last page to cycle through a stable finite set; concurrent changes do not provide snapshot fairness. A returned cursor means the page was full and a following page might still be empty. Each candidate must also be passed to `check`; discovery itself never expires rows. The observations map is currently unbounded, so it is unsuitable for a long-lived scanner processing unbounded distinct keys; a bounded strategy must be designed and tested without starving stable sets before integration.

## Synthetic benchmark

Run `node --import tsx scripts/experimental-429-incremental-benchmark.mjs`. It creates a file in Hermes scratch, inserts 100,000 synthetic rows (99,000 indefinite), reports the actual indexed statement's query plan and one 10-row page call, then deletes the fixture. Its latency includes schema validation and transaction setup, is a single warm-cache sample, and is not a production measurement; SQLite cache and file-system I/O conditions can dominate results.
