# Experimental offline OPEN-schema provisioning

**Not approved for production.** Phase 4 and this utility require independent review and the remaining project safety work. Do not run against a real database until separately authorized. This utility does not run automatically on startup. It adds ordinary and SIWC OPEN tables and markers for the pre-OPEN baseline, or only SIWC objects for the ordinary-only baseline; normal application initialization performs other migrations later.

## Separate 429 cutover prerequisite — disabled

`scripts/offline-429-upgrade.mjs` is a staged operator entrypoint, **hard-disabled**, and not wired into this OPEN utility, startup, selection, settlement, or expiry. Do not enable or run it against a real database pending independent review, integration testing and separate explicit authorization. The existing OPEN commands below do not perform 429 migration. The staged path refuses an ambient transaction, opens only an explicitly specified existing absolute file with `fileMustExist`, obtains a top-level `BEGIN IMMEDIATE`, calls the real migration and validates with the real v2 store before commit. Errors escape the transaction and cause rollback; a commit error may have an uncertain outcome. It does not import application configuration or dotenv.

The entrypoint requires distinct operator attestations: `--backup-verified`, `--all-routers-stopped`, `--no-outstanding-work`, `--legacy-schema-provenance-verified`, and `--single-host-trusted-directory`. These are claims, not facts the program verifies. A consistent backup including WAL must be verified restorable; all routers and in-flight or unknown-outcome work must be stopped/drained, all versions must remain stopped throughout cutover, and the database must have the genuine expected prior schema provenance. A SQLite lock cannot prevent an old binary reconnecting. Legacy cooldowns, including expired and orphaned rows, become **indefinite** restrictions, potentially reducing availability; legacy rows and all OPENs remain untouched.

For the narrowly recognized `740df93` pre-429 baseline after pre-OPEN provisioning, the staged helper additionally requires `--genuinely-pre-429`. It verifies complete stored schema SQL and mandatory markers before creating an empty legacy cooldown table within the same transaction as the v2 and usage upgrades. This option is an operator attestation that the database genuinely predates the 429 table, **not** proof inferred from a missing table: later deleted safety history can look identical. See [ADR 0013](./adr/0013-pre-429-historical-upgrade.md). Do not use this as an operator command while the CLI is disabled.

Path checks reject detected links and compare file identity, but SQLite opens by path, not by the checked descriptor: replacement between checks, hard links, Windows reparse points and ancestor races are not eliminated. A protected single-host directory, including DB/WAL/SHM files, is an operator prerequisite. OS-level opening, file-backed startup, crash and durable-commit behavior have not been verified by the in-memory tests. Fresh startup remains unsupported: a pre-existence check cannot attest pristine ownership, and a v2-only database is nonempty and fails OPEN provisioning validation. Do not manufacture a v2-only file or bypass validation. Safe fresh provisioning requires an independently reviewed exclusive-create/identity design and atomic initialization of all application and v2 schemas.

The staged 429 helper and the separate OPEN provisioning and recovery tools now reject a main DB file whose observed hard-link count is not exactly one, and recheck the descriptor and path before completion. On Windows, owned-file tests verified rejection of an existing hard link for each tool, and rollback when a link was created during the 429 helper's transaction. This does not prevent a link being created and removed between checks or after the final check; it does not establish the identity of SQLite's separately opened handle or cover WAL/SHM links. Keep all existing offline-directory and router-stop prerequisites. See [ADR 0014](./adr/0014-offline-hard-link-checks.md).

**Focused Windows file-backed evidence:** The isolated `phase4-offline-app-schema-migration.test.mjs` wrapper completed 1/1 with ten internal cases, including the two hard-link checks above. Two other cases use an owned WAL SQLite file and actual filesystem identity checks through the disabled CLI's injectable helper: one tests a second connection holding the writer lock, then migrates, closes and reopens; the other injects an SQLite statement failure after both the v2 write and a partial usage copy, then compares schema, index metadata, rows and journal mode after reopening. The successful case also runs the actual initializer logic and validators through a VM with the owned file-backed handle injected. This is not a separate application-process startup, a real crash or disk failure, a two-process startup race, or an adversarial filesystem race test. The fixture uses current application initialization with historical usage DDL, not a complete historical schema. The operator CLI remains hard-disabled and no production database was used.

**Historical baseline and separate initializer:** `phase4-historical-cutover.test.mjs` passed 1/1 on a test-owned file with the stored `740df93` initialized schema and synthetic records, using the OPEN CLI, the staged helper with the additional attestation, and a separate process running the current DB initializer. It checks negative schema/marker controls, injected rollback, historical rows and 64-bit token values. Its initializer uses native Node TypeScript transformation and a test resolver, not the packaged production server. The JS process/network guards are not an OS sandbox. Actual operator databases, provider compatibility, crash durability and path-replacement races remain unverified.

The accepted baselines are the initialized database from commit `740df936887f40efc727a24b159064bfd4db34e5`, and an ordinary-only database with an intact ordinary marker. For the latter, the tool recognizes exactly two schema variants: the historical baseline plus the prior upgrader's ordinary objects, or the current schema frozen in `scripts/current-ordinary-only-schema.json` (captured from synthetic current-client initialization with the SIWC pair removed). Exact recognition includes all SQLite schema objects and their SQL tokens, implicit indexes, metadata, integrity and foreign-key checks, and the applicable initialized markers. Other legitimate versions or migration histories can be rejected. Schema is not proof of provenance: deleting both SIWC objects from a newer database can recreate the same appearance. A recognized schema cannot prove no requests are outstanding or no OPEN was lost.

The operator must independently confirm every router process is stopped and remains stopped throughout the cutover, all work is resolved (including in-flight and unknown-outcome requests), a consistent backup including relevant WAL state is verified and restorable, and the selected database provenance is genuine. Ordinary OPEN rows, including unknown-outcome rows, are preserved, never deleted or resolved by this utility; their existence is not evidence that work is resolved. The SQLite writer lock is temporary and **cannot prevent an old router or another version from reconnecting afterwards**; the tool cannot enforce binary versions. Do not proceed if any fact is unknown.

Only after review and explicit authorization, invoke exactly one of the following with one existing database file and all four attestations:

```
node scripts/offline-open-upgrade.mjs --all-routers-stopped --no-outstanding-work --backup-verified --genuinely-pre-open PATH_TO_EXISTING_DB
node scripts/offline-open-upgrade.mjs --all-routers-stopped --no-outstanding-work --backup-verified --genuinely-pre-siwc-open PATH_TO_EXISTING_DB
```

It refuses unrecognized objects, metadata, missing quota initialization, corrupt or FK-inconsistent databases, collisions, a missing file, or competing writers. Validation and additions occur inside one exclusive SQLite transaction. Rejected attempts do not deliberately change journal mode. Commit errors may leave the outcome uncertain: inspect the database and verified backup before deciding what to do. It does not print existing rows or credentials. Do not delete a marker or an OPEN record to make the tool accept a database.

The path must be a normal existing file, not a SQLite URI; every resolved component is checked with lstat and symlinks/junctions are rejected. Device/inode identity is compared before and after opening SQLite and again while holding the writer lock. On POSIX a separate read-only probe uses O_NOFOLLOW where available; SQLite itself opens by path, not that descriptor. Windows has no equivalent no-follow SQLite open here, and Node's link detection may not cover every reparse-point type. These checks are not atomic and do not protect against an adversary replacing a path between checks (including after the final check); no claim of race-proof operation or unchanged files under adversarial replacement is made. Use an offline directory and DB/WAL files protected by OS permissions from any other user or process capable of modifying or replacing them, and stop all writers. Identity checks may refuse filesystems without usable IDs. The backup attestation is operator-supplied, not verified by the utility; a synthetic WAL backup test does not verify an operator's backup.
