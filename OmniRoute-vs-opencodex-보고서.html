01

라우터가 뭐예요?

AI 도구마다 쓰는 "말투"(API 형식)가 다릅니다. 라우터는 가운데 앉아서 말투를 통역하고, 어느 모델로 보낼지 고르고, 계정과 키를 관리합니다.

자세히: 왜 통역이 어려운가 형식 세 가지의 차이

요즘 코딩 도구가 쓰는 형식은 크게 셋입니다. 겉보기엔 비슷해도 담을 수 있는 정보가 다릅니다.

형식쓰는 도구특징통역할 때 문제
OpenAI ResponsesCodex CLI·App출력이 "항목(item)" 단위. reasoning 항목, encrypted_content, custom tool(apply_patch), compaction, web_search 같은 전용 기능다른 제공자에는 이 기능들이 없음
Anthropic MessagesClaude Codecontent block 단위. thinking 블록에 서명(signature)이 붙고, 다음 턴에 그대로 돌려보내야 함서명을 잃으면 400 오류
OpenAI Chat CompletionsCursor·Cline 등 대부분가장 흔하지만 가장 단순. reasoning 자리가 표준에 없음정보를 담을 칸이 부족

그래서 "어떤 형식을 중간 기준(허브)으로 삼느냐"가 두 프로젝트를 가르는 가장 큰 설계 결정입니다. 06 번역 허브에서 자세히 봅니다.

03

요청 하나가 지나가는 길

컨베이어 벨트에 비유하면 단계 수는 둘 다 일곱 개쯤입니다. 차이는 가운데서 무엇을 들고 다니느냐입니다. OmniRoute는 OpenAI Chat JSON을, opencodex는 자기만의 타입 IR을 들고 다닙니다.

OmniRoute 경로 상세
  1. 인증 게이트: src/proxy.ts(Next 미들웨어)가 runAuthzPipeline을 실행합니다. /V1/처럼 대문자로 우회하던 취약점(GHSA-jvqc-mp9f-q936) 이후 대소문자 무시 매칭으로 바뀌었습니다. next.config.mjs가 /v1/*를 /api/v1/*로 다시 씁니다.
  2. 라우트 핸들러: /v1/chat/completions, /v1/messages, /v1/responses가 모두 src/sse/handlers/chat.ts의 handleChat으로 모입니다. 각 핸들러가 API 키를 다시 확인하고, 프롬프트 인젝션 가드·입장 제어·초기 keepalive를 거칩니다.
  3. 모델 해석: 별칭을 풀고, 모델 이름이 콤보면 open-sse/services/combo.ts의 handleComboChat, 아니면 handleSingleModelChat으로 갑니다. 단일 모델도 계정 선택을 반복하며 실패한 연결을 빼고 토큰을 갱신합니다.
  4. 핵심 실행: open-sse/handlers/chatCore.ts(3,362줄 + 하위 모듈 약 170개)가 형식 감지 → 압축 → 시맨틱 캐시·멱등성 → translateRequest → executor 조회 → 전송(세마포어, 시작 타임아웃, 스트림 복구) 순으로 처리합니다.
  5. 업스트림: open-sse/executors/base.ts의 BaseExecutor.execute()가 URL·헤더·본문을 만들고 프록시 경유 fetch를 합니다. 제공자별 executor가 약 200개(웹 세션용 *-web.ts 25개 포함).
  6. 응답: open-sse/utils/stream.ts(3,404줄)가 SSE를 파싱해 이벤트마다 translateResponse를 부릅니다.
opencodex 경로 상세
  1. 리스너: src/server/index.ts의 Bun.serve. 기본 127.0.0.1:10100. 새로 설치하면 제공자가 openai(ChatGPT 백엔드, forward 모드) 하나뿐입니다.
  2. Responses 경로: responses/policy-fallback.ts → responses/core.ts:handleResponses → core-pipeline.ts. responses/parser.ts:parseRequest가 본문을 IR로 바꾸고 router.ts:routeModel이 대상을 정합니다.
  3. 분기: 진짜 OpenAI면 거의 그대로 통과(passthrough). 아니면 사이드카(웹 검색·비전·이미지) → runTurn형 어댑터 또는 buildRequest/parseStream형 어댑터.
  4. 어댑터 계약(src/adapters/base.ts): buildRequest(IR) → HTTP 요청, parseStream(Response) → AsyncGenerator<AdapterEvent>. 와이어 계열 11개(openai-chat, openai-responses, anthropic, google, kiro, cursor, devin, zed, ollama-native, codebuddy, command-code).
  5. 출력: bridge/sse.ts:bridgeToResponsesSSE가 이벤트를 Responses SSE로 인코딩합니다.
  6. Claude Code 경로: claude-messages.ts가 Anthropic 본문을 내부 /v1/responses 요청으로 바꿔 같은 파이프라인을 태운 뒤, claude/outbound.ts가 Responses SSE를 다시 파싱해 Anthropic SSE로 바꿉니다. Chat Completions도 같은 방식입니다.
  7. WebSocket: Codex 쪽 response.create 프레임을 같은 파이프라인으로 받고, ChatGPT 백엔드로는 wss://로 나갈 수 있습니다(기본 꺼짐).
04

어디로 보낼까: 라우팅과 폴백

"콤보"는 후보 모델 목록입니다. 앞 후보가 할당량 초과나 서버 오류로 실패하면 다음 후보로 넘어갑니다. 단, 답이 한 글자라도 나간 뒤에는 넘어가지 않습니다.

OmniRoute 라우팅 상세

콤보 전략(open-sse/services/combo/strategyRegistry.ts): priority, weighted, round-robin, context-relay, fill-first, p2c, random, strict-random, least-used, cost-optimized, reset-aware, reset-window, headroom, quota-weighted, quota-share, auto, lkgp, context-optimized, cache-optimized, fusion(여러 모델 + 심판), pipeline(앞 모델 출력을 다음 입력으로). 전략마다 정렬·고정·예약·프롬프트 캐시 친화도 같은 특성을 가집니다.

auto: autoCombo/scoring.ts가 할당량·상태·비용·지연·작업 적합도·안정성·컨텍스트/캐시 친화도·리셋 창·품질 등을 가중 합산합니다. auto/coding, auto/fast, auto/cheap, auto/subscription 같은 변형이 있습니다.

계정 선택(src/sse/services/auth.ts): 기본 fill-first. round-robin, p2c, random, least-used, expiry-first, cost-optimized, strict-random.

실패 처리: accountFallback.ts(2,565줄)가 정규식으로 오류를 분류합니다(차단 계정, 크레딧 소진, 토큰 무효, 컨텍스트 초과, 속도 제한, 모델 단위 400). 지수 백오프, Retry-After, 서킷 브레이커, 제공자별 할당량 조회기 약 30개, 차단 계정 자동 비활성화가 있습니다.

opencodex 라우팅 상세

모델 해석 순서(router.ts:routeModelInternal): ① policy/<id> 프로필 ② Codex 계정 네임스페이스(acct/gpt-*) ③ 콤보 ④ provider/model ⑤ gpt-*·o3- 등은 openai ⑥ 제공자 기본 모델 ⑦ 접두사 패턴 ⑧ 모델 목록 ⑨ 별칭(모호하면 오류) ⑩ 기본 제공자.

콤보 전략: failover, round-robin, random, least-used, reset-window, jev(외부 결정 서비스가 대상과 effort를 고름, 기본 api.typesafe.ai).

OCX-11 폴백 정책(src/routing/fallback-policy.ts): 폴백을 범위별로 끌 수 있습니다. 우선순위는 라우트 > 제공자 > 전역. 거부되면 fallback_refused와 x-opencodex-fallback: refused 헤더. 같은 풀 안의 계정·키 순환은 끌 수 없는 "내부 복원력"으로 따로 취급합니다.

재시도(lib/upstream-retry.ts): 최초 1회 + 일시 오류 재시도 2회. 출력이 관찰되면 재전송 금지(request-resend-gate.ts).

ChatGPT 계정 풀: 스레드·캐시 친화도로 대화 중 계정이 바뀌지 않게 하고, 할당량 임계치로 순환합니다.

opencodex는 $CODEX_HOME/config.toml에 openai_base_url(루프백), 모델 카탈로그 경로, 실시간 WS 주소를 넣고, 주입 기록(opencodex-journal.json)을 남기며 codex 실행 shim을 설치합니다. ocx stop·restore로 원상복구합니다. Claude Desktop은 OS 키체인에 CA를 신뢰시키고 claude.ai를 가로챕니다.

OmniRoute는 CLI가 Claude Code·Codex·Cursor·Cline 설정을 자동으로 고쳐 OmniRoute를 가리키게 합니다. 더 나아가 src/mitm/이 루트 CA를 OS에 설치하고 hosts 파일을 관리자 권한으로 고친 뒤 :443에서 api.anthropic.com, cloudcode-pa.googleapis.com, Copilot·Cursor·Codex 호스트를 가로챕니다. 리눅스용 iptables TPROXY + C 애드온도 실험 단계로 있습니다.

06

번역의 심장: 중간 기준(허브) 고르기

통역사가 머릿속에서 어떤 언어로 생각하느냐의 문제입니다. 단어가 적은 언어로 생각하면 뜻이 빠집니다. OmniRoute는 칸이 적은 Chat 형식으로 생각해서 Claude의 "서명"이 중간에 사라집니다.

자세히: 두 허브의 실제 코드

opencodex: 타입 IR (src/types/request.ts)

  • 메시지 역할을 user | assistant | developer | toolResult 넷으로 정규화합니다.
  • assistant 내용은 text | thinking | toolCall 파트 배열. thinking에 signature와 redacted[], toolCall에 Gemini용 thoughtSignature가 있습니다.
  • 응답은 이벤트 합 타입: heartbeat, text_delta(phase?), thinking_delta, thinking_signature, redacted_thinking, reasoning_raw_delta, tool_call_start/delta/end, web_search_call_begin/end, done, incomplete, error.
  • 약점: 요청 IR에 _로 시작하는 임시 필드가 50개 넘게 붙어 있습니다. 제공자별 상태가 IR로 새어 들어온 흔적입니다.

OmniRoute: 레지스트리 + Chat 허브 (open-sse/translator/)

  • registry.ts는 "from:to" 키로 요청 번역기와 응답 번역기를 담는 Map 두 개입니다. 타입은 Record<string, unknown>.
  • translateRequest(index.ts:342): 원본과 대상이 둘 다 OpenAI가 아니고 직접 번역기가 있으면 그걸 쓰고, 아니면 원본 → OpenAI → 대상. 중간 정보는 credentials 객체에 _targetFormat, _preserveReasoningContent, _signatureNamespace, _ensureUserTurn을 끼워 넘깁니다.
  • translateResponse: 청크마다 같은 방식. 두 단계가 state 객체 하나를 공유합니다.
  • 번역기 코드 약 2.4만 줄. 가장 큰 파일은 response/openai-responses.ts(1,577줄), request/openai-to-kiro.ts(1,131줄).

끝맺기와 오류: 첫 글자가 경계선

답이 한 글자도 안 나갔으면 다른 계정·모델로 다시 시도해도 됩니다. 한 글자라도 나갔으면 다시 시도하면 안 됩니다. 사용자가 같은 말을 두 번 보게 됩니다.

자세히: 종료 처리 비교
  • opencodex: Chat 업스트림이 [DONE]도 finish_reason도 없이 끊기면 "잘렸을 수 있음" 오류(openai-chat.ts:658). 거부(refusal)는 response.failed로, 할당량 초과 등은 retryable 표시. 이미 발행된 tool call은 실패 전에 completed로 닫아 클라이언트가 호출을 잃지 않게 합니다.
  • opencodex의 Anthropic 출력은 message_start → (블록 시작·델타·종료)* → message_delta → message_stop 순서를 고정하고, message_delta.usage는 누적값입니다.
  • OmniRoute: 초기 keepalive 프레임, 스트림 복구(services/streamRecovery.ts)가 있습니다. finish_reason은 computeFinishReason(state)가 플래그로 추론합니다(tool call이 있었으면 tool_calls, 잘렸으면 length).
설계 포인트

종료 이벤트는 done | incomplete | error 셋만 두고, 그 밖의 스트림 종료는 전부 incomplete로 처리하세요. "첫 출력 전/후" 경계는 타입이나 게이트 하나로 표현하세요.

직접 라우터를 만든다면

opencodex의 뼈대를 가져오되 더 작게. 들어오는 통역사 N명, 나가는 통역사 M명, 가운데 공통 언어 하나. 그러면 통역 규칙은 N×M개가 아니라 N+M개면 됩니다.

  1. IR은 타입으로, 작게

    opencodex 구조(역할 4개, 파트 3종)를 가져오되 제공자별 상태는 providerState 하나로 모으세요. _ 필드가 50개로 불어나지 않게.

  2. 응답은 이벤트 합 타입

    text_delta(phase?), thinking_delta, thinking_signature, redacted, tool_call_start/delta/end, heartbeat, 그리고 종료 셋 done | incomplete | error.

  3. 어댑터가 지저분한 일을 전담

    병렬 tool call 직렬화, <think> 분리, 텍스트로 쓴 tool call 복구, 대화 모양 규칙. 전부 해당 제공자 어댑터 안에서.

  4. 인코더는 열린 항목 하나

    phase는 다음 이벤트를 보고 사후 분류, 서명은 다음 이벤트까지 보류, tool call 인자는 검증 후 완료.

  5. reasoning은 HMAC 봉투

    대상(제공자·모델·자격증명)이 바뀌면 폐기. 서버 캐시는 DeepSeek 계열 보조용으로만.

  6. 첫 출력 게이트

    재시도·폴백은 첫 바이트 전까지만. 이 규칙을 한 곳에서.

  7. 바이트 예산

    opencodex의 TranslatorBudget처럼 버퍼·봉투·누적기에 상한을. 긴 세션 프록시에서 메모리 누수는 실제 문제입니다.

  8. 녹화·재생 골든 테스트

    실제 업스트림 SSE를 저장해 두고 재생해서 비교하세요. 두 프로젝트의 이슈 번호 붙은 회귀 테스트 수천 개 대부분이 이 방식으로 미리 잡을 수 있는 버그였습니다.

// 요청 IR
type Part =
  | { type: "text"; text: string }
  | { type: "thinking"; text: string; signature?: Envelope; redacted?: string[] }
  | { type: "toolCall"; id: string; name: string; args: unknown };

type Message =
  | { role: "user" | "developer"; content: string | ContentPart[] }
  | { role: "assistant"; content: Part[] }
  | { role: "toolResult"; callId: string; content: string | ContentPart[]; isError: boolean };

interface ParsedRequest {
  model: string;
  system: string[];
  messages: Message[];
  tools: Tool[];
  options: { maxOutput?: number; effort?: string; toolChoice?: ToolChoice };
  providerState?: Record<string, unknown>;   // 제공자별 상태는 여기 한 곳만
}

// 응답 이벤트
type Event =
  | { type: "heartbeat" }
  | { type: "text_delta"; text: string; phase?: "commentary" | "final_answer" }
  | { type: "thinking_delta"; text: string }
  | { type: "thinking_signature"; signature: string }
  | { type: "redacted"; data: string }
  | { type: "tool_call_start"; id: string; name: string }   // 어댑터가 한 줄로 세워서 보냄
  | { type: "tool_call_delta"; args: string }
  | { type: "tool_call_end" }
  | { type: "done"; usage?: Usage; stopReason?: string }
  | { type: "incomplete"; reason: string; usage?: Usage }
  | { type: "error"; message: string; status?: number; retryable?: boolean };

interface Adapter {
  buildRequest(req: ParsedRequest): { url: string; headers: Record<string, string>; body: string };
  parseStream(res: Response): AsyncGenerator<Event>;
}

// 봉투: 대상이 바뀌면 검증 실패 → 폐기
interface Envelope { v: 1; provider: string; model: string; cred: string; sig?: string; red?: string[]; mac: string }

구독 위장기술 문제가 아니라 계정 정지 문제입니다. API 키 경로로 설계하세요.
