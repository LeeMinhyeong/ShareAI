# 다계정 AI 라우터

여러 사용자가 여러 AI 계정(Claude, GPT, Gemini)을 공유하여 사용할 수 있는 라우팅 서버입니다.

**OmniRoute**와 **opencodex** 분석을 기반으로 설계되었습니다.

## 🎯 핵심 기능

- ✅ **다계정 풀 관리**: A, B, C 계정을 여러 사용자가 공유
- ✅ **자동 로드밸런싱**: 라운드로빈, 우선순위, 최소 사용 전략
- ✅ **할당량 추적**: 계정별 일일 한도 자동 감지
- ✅ **사용자 격리**: 사용자별 API 키 및 사용량 추적
- ✅ **프로토콜 번역**: OpenAI Chat ↔ Anthropic Messages ↔ Responses
- ✅ **자동 폴백**: 429 에러 시 다른 계정으로 자동 재시도

## 📐 아키텍처

```
사용자1, 2, N → 라우터 서버 (인증 + 계정 풀 관리) → 계정 A, B, C → Claude/GPT/Gemini
```

자세한 설계는 **[다계정-라우터-설계.md](./다계정-라우터-설계.md)** 참조.

### 3. 데이터베이스 초기화

현재 SQLite만 지원합니다. `.env`에 `DATABASE_URL=sqlite:./data/router.db`를 설정한 후 실행하세요.
서버 시작 시에도 listen 전에 스키마 초기화와 기존 DB 마이그레이션이 실행되어 DB가 변경될 수 있습니다. 중요한 데이터는 백업하고, 테스트에는 별도의 DB를 사용하세요. **기존 운영 DB를 업그레이드할 때는 아래 오프라인 절차를 먼저 수행하세요.**

```bash
npm run db:migrate
```

#### 기존 DB 할당량 마이그레이션: 필수 오프라인 전환

**운영 전제 조건이며 자동으로 강제되지 않습니다.** 마이그레이션은 기존 성공 `usage_logs`를 사용자·UTC 날짜별 할당량에 **한 번만** 반영합니다. 그 뒤 구버전 프로세스나 전환 전 진행 중이던 요청이 성공 로그를 추가하면 재시작이나 마이그레이션 재실행으로 그 누락분이 반영되지 않아 한도를 초과할 수 있습니다. DB 잠금은 구버전의 추후 접근을 막지 않습니다. 롤링 배포 또는 구·신버전 혼용은 금지합니다.

1. 점검 시간을 확보하고 로드 밸런서, 클라이언트 및 재시도 큐에서 새 요청 유입을 차단합니다. 모든 호스트·컨테이너의 자동 재시작, 스케줄러와 배포를 일시 중지합니다. 진행 중인 요청과 스트리밍, 백그라운드 작업이 모두 끝날 때까지 기다리고, 종료가 확인되지 않거나 강제 종료로 결과가 불명확하면 중단하여 확인·조정합니다.
2. 같은 DB에 접근할 수 있는 **모든 구버전 및 신버전 서버, 워커, 관리 작업과 기타 writer**를 중지합니다. 전체 인스턴스의 종료와 DB 연결 종료를 운영 환경에서 확인하고, 전환이 끝날 때까지 재시작을 막습니다. 일부만 중지하거나 신버전 서버를 먼저 실행하지 마세요.
3. 정지 상태에서 실제 대상 `DATABASE_URL`을 확인하고 복구 가능한 백업을 만듭니다. SQLite는 WAL 모드이므로 DB 파일만 임의로 복사하지 말고 SQLite 백업 API 등 일관된 백업을 사용하거나, 모든 연결이 닫힌 것을 확인한 뒤 DB와 필요한 `-wal`/`-shm` 파일을 함께 보존합니다. 별도 위치에 복원하여 무결성과 필요한 데이터 및 복구 가능성을 확인하고 백업을 안전하게 보관합니다. 실패하면 진행하지 마세요.
4. 백업의 별도 복사본으로 먼저 시험합니다. 이후 **모든 서비스가 정지된 상태에서** 올바른 작업 디렉터리와 운영 설정(`DATABASE_URL`, 필수 환경 변수)을 확인하고 신버전 코드로 `npm run db:migrate`를 단 한 번 실행합니다. 종료 코드가 0인지 확인하고 오류가 있으면 서비스를 시작하지 말고 원인을 해결합니다. 자동 서버 시작도 마이그레이션을 실행하므로 이 단계 전에는 시작하지 않습니다.
5. 서비스가 아직 정지된 상태에서 대상 DB의 `quota_migration_marker`에 `id = 1`이 있는지 확인하고, 백업의 성공 로그를 사용자·UTC 날짜별로 집계한 값과 새 `user_daily_quota.used`를 비교합니다. 불일치나 누락, 잘못된 timestamp가 있으면 트래픽을 열지 말고 조사합니다. 시험용 DB가 아닌 운영 DB를 검사했는지도 확인합니다.
6. 검증이 끝나면 신버전만 배포·시작하고 인스턴스 버전과 DB 대상을 확인한 뒤 트래픽과 자동 재시작을 다시 켭니다. 이후에도 구버전 프로세스, 관리 도구 또는 별도 writer가 같은 DB에 접근하지 못하도록 운영상 통제합니다.

**롤백 주의:** 구버전을 마이그레이션된 DB에 그대로 연결하는 것은 안전한 롤백이 아닙니다. 신버전도 모두 중지·drain한 후 검증된 전환 전 백업으로 복원하고, 백업 이후의 요청·할당량 사용, 계정 변경 및 외부 제공자 토큰 회전 등은 복원으로 사라지거나 실제 상태와 어긋날 수 있으므로 서비스 재개 전 별도로 조사·조정해야 합니다. 복원이 가능하다는 전제나 데이터 무손실을 보장하지 않습니다. 운영 환경의 모든 writer 중지와 복구 가능성은 이 절차로도 자동 검증되지 않는 잔여 위험입니다.

### 4. 서버 실행

```bash
# 개발 모드 (핫 리로드)
npm run dev

# 프로덕션 빌드
npm run build
npm start
```

서버가 `http://localhost:20100`에서 실행됩니다. `GET /health`는 프로세스의 liveness 확인이며 DB 상태나 외부 제공자 연결을 검사하는 readiness 검사가 아닙니다.

종료 신호를 받으면 신규 토큰 갱신을 거부하고 진행 중인 갱신의 저장과 HTTP drain을 기다린 뒤 DB를 닫습니다. OAuth 로그인 교환은 종료 시 취소하고 처리 완료를 기다리며, 로그인 교환 및 프로필 조회에는 각각 10초 제한을 둡니다. 단, 전체 종료 제한시간은 5초입니다. 그 안에 갱신 교환이 완료되지 않으면 프로세스는 오류 코드로 강제 종료되며, 제공자가 이미 refresh token을 회전했다면 새 토큰이 저장되지 않아 재로그인이 필요할 수 있습니다. 제한시간은 무한 대기 방지와 토큰 보존 사이의 절충입니다. 네트워크 응답 유실, SIGKILL이나 프로세스 장애까지 포함하여 제공자의 회전과 로컬 저장을 원자적으로 보장할 수는 없습니다. 관리자가 갱신 중 자격증명을 교체하면 이전 갱신 결과는 덮어쓰지 않고 버립니다. 이 경우에도 제공자 측에서 이전 토큰을 이미 회전했을 수 있습니다.

## 📚 사용법

### 계정 추가 (관리자)

```bash
curl -X POST http://localhost:20100/admin/accounts \
  -H "Authorization: Bearer admin_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Claude-A",
    "provider": "anthropic",
    "credentialType": "api_key",
    "credentials": "sk-ant-api03-...",
    "dailyQuota": 1000,
    "priority": 0
  }'
```

### 사용자 추가

```bash
curl -X POST http://localhost:20100/admin/users \
  -H "Authorization: Bearer admin_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "사용자1",
    "email": "user1@example.com",
    "tier": "pro",
    "dailyLimit": 500
  }'

# 응답에서 apiKey를 저장
```

### AI 요청 보내기

```bash
# OpenAI Chat 형식
curl -X POST http://localhost:20100/v1/chat/completions \
  -H "Authorization: Bearer user_abc123..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-3-5-sonnet-20241022",
    "messages": [
      {"role": "user", "content": "안녕하세요"}
    ],
    "stream": true
  }'
```

## 🛠️ 개발 로드맵

코드 리뷰에서 분리한 개선 사항과 미검증 항목은 **[개선 백로그](./BACKLOG.md)**에서 관리합니다.

현재 작업 초점은 **Phase 2 저장소와 인증**입니다. Phase 3 구독 계정 연결 등 다른 Phase의 일부 기능은 병행 개발된 상태입니다.

각 Phase는 **개발 → 코드 리뷰 및 발견 사항 처리 → 테스트 → 완료** 순서로 진행합니다. 테스트 전에 코드 리뷰를 수행하고, 리뷰에서 발견한 문제를 처리한 뒤 해당 Phase의 완료 기준에 따른 테스트를 실시합니다. 구현만 끝났거나 리뷰·테스트가 남아 있는 Phase는 완료로 표시하지 않습니다. 상태는 미착수 → 구현 중 → 코드 리뷰 중 → 테스트 중 → 완료로 관리합니다.

| Phase | 목표 | 완료 기준 | 현재 상태 |
|---|---|---|---|
| **1. 기반 구조** | 서버, 프로젝트 구조, 기본 설정 | 서버 기동·빌드·헬스체크 통과 | 완료: 독립 리뷰 및 격리 테스트 확인 |
| **2. 저장소와 인증** | DB, 계정·사용자 관리, 자격증명 암호화 | CRUD·마이그레이션·인증·암호화 테스트 통과 | 완료: 독립 리뷰 및 격리 테스트 확인 |
| **3. 구독 계정 연결** | Claude·ChatGPT 계정 로그인, 가져오기, 토큰 갱신 | 각 제공자의 실제 구독 계정으로 로그인하고 요청 성공 | 구현 중 / 실제 계정 검증 미완료 |
| **4. 라우팅과 자동 전환** | 전략 선택, 계정 상태·할당량, 429/5xx 전환 | 다중 계정 테스트에서 선택·쿨다운·자동 전환 확인 | 일부 구현 / 자동 전환 미완료 |
| **5. 클라이언트 호환** | Claude Code·Codex 요청/응답, 스트리밍, thinking, tool call | 각 CLI/App에서 실제 작업과 스트리밍·도구 호출 검증 | 일부 구현 / 대부분 미검증 |
| **6. 대시보드와 운영** | 계정·사용자·통계 UI, 모니터링, 배포·보안 | UI 연동, 사용량·상태 표시, 재시작·보안·운영 테스트 통과 | 대시보드 기본 구현 / 운영 검증 미완료 |

> 기존 설계 문서의 4단계 로드맵은 초기 구상입니다. 현재 진행 관리는 위 6단계를 기준으로 합니다.

### Phase 1. 기반 구조

**목표:** 서버, 프로젝트 구조, 기본 설정을 마련합니다.  
**현재 상태:** 완료. 별도 에이전트의 코드 리뷰와 지적 사항 수정 후, `npm test` 95건 통과 및 `npm run build` 성공을 확인했습니다. 테스트는 격리 DB와 모의 업스트림을 사용했으며 헬스체크는 의존성 준비 상태가 아닌 서버 응답성(liveness)만 확인합니다. 실제 구독 계정 검증은 Phase 3에 남아 있습니다.

- 서버 진입점과 프로젝트 디렉터리 구조 구성
- 환경 변수와 기본 서버 설정 구성
- **완료 기준:** 서버 기동·빌드·헬스체크 통과

### Phase 2. 저장소와 인증

**목표:** DB, 계정·사용자 관리, 자격증명 암호화를 구현합니다.  
**현재 상태:** 완료. 별도 에이전트의 코드 리뷰 및 지적 사항 수정과 수정 범위 재리뷰 후, 격리 환경에서 전체 `npm test` 145건 통과 및 `npm run build` 성공을 확인했습니다. 기존 운영 DB 전환은 위 오프라인 절차를 따라야 하며, 레거시 평문 또는 복호화할 수 없는 자격증명은 자동 신뢰·변환하지 않아 관리자의 재등록이 필요합니다. 실제 구독 계정 검증은 Phase 3에 남아 있습니다.

- 계정·사용자 및 사용 기록을 저장하는 DB 구성
- 계정과 사용자 관리 기능 및 인증 처리
- 자격증명 암호화와 기존 데이터 마이그레이션 처리
